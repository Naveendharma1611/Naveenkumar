Module 1 — DBMS Foundations

DBMS vs database · Responsibilities · Users

▼

Database, DBMS, and SQL

A database is an organized collection of data. A Database Management System (DBMS) is software that defines, stores, queries, protects, and recovers that data. SQL is a language used with many relational DBMSs; a DBMS is the larger system that also handles storage, transactions, concurrency, security, and recovery.

ConcernDBMS responsibility
DefinitionSchemas, constraints, metadata, and data types
StorageFiles, pages, indexes, buffers, and durable writes
QueriesParse, optimize, and execute requests
TransactionsCoordinate concurrent work with defined guarantees
ProtectionAuthentication, authorization, auditing, and recovery

Why Use a DBMS?

A DBMS centralizes integrity rules, access control, concurrent access, and recovery instead of leaving every application to implement them independently. The right design still depends on workload, consistency requirements, operating cost, and failure assumptions.

Module 2 — Database Architecture & Abstraction

Schemas · Instances · Data independence

▼

Three-Schema Architecture

The external level describes user or application views, the conceptual level describes the logical database, and the internal level describes physical storage. Mappings between levels help separate application concerns from storage details.

LevelDescribes
ExternalA particular user's or application's view
ConceptualEntities, relationships, constraints, and logical structure
InternalFiles, pages, indexes, compression, and physical placement

Data Independence

Logical data independence means changing the conceptual schema without requiring changes to every external view. Physical data independence means changing storage structures without changing the logical schema or application meaning. Both are goals, not guarantees that every schema change is invisible.

  1. Give an example of a physical storage change that should not alter an application's logical query.
  2. Which schema level describes the logical relationships among entities?

Module 3 — Data Models & ER Design

Entities · Attributes · Relationships · Cardinality

▼

Conceptual Modeling

An Entity-Relationship model describes entities, their attributes, relationships, and participation/cardinality constraints before choosing a physical representation. Define the business meaning and grain precisely so the eventual schema reflects the real domain.

ConceptExample
EntityCustomer, Order, Product
AttributeCustomer email, order date, product SKU
RelationshipCustomer places Order
CardinalityOne customer to many orders
ParticipationWhether an entity must take part in a relationship

Convert Relationships into Relations

A one-to-many relationship commonly places a foreign key on the many side. A many-to-many relationship commonly uses a junction relation whose key represents a pair of related entities, possibly with attributes of its own.

State whether relationship cardinality is one-to-one, one-to-many, or many-to-many and whether participation is optional before designing constraints.

Module 4 — Relations, Keys & Integrity Constraints

Candidate keys · Foreign keys · Constraints

▼

Keys

A superkey uniquely identifies rows but may contain unnecessary attributes. A candidate key is a minimal superkey; one candidate is selected as the primary key. A foreign key constrains references to another candidate or primary key, subject to the DBMS's rules.

KeyRole
SuperkeyAny attribute set that uniquely identifies a tuple
Candidate keyMinimal superkey
Primary keyChosen candidate key for row identification
Alternate keyCandidate key not selected as primary
Foreign keyEnforces a reference to a key in a related relation
Composite keyKey formed from multiple attributes

Integrity Constraints

Entity integrity requires a primary-key value to identify each row; referential integrity keeps references valid; domain constraints restrict permitted values. Unique, check, not-null, and foreign-key constraints encode rules close to the data.

CREATE TABLE enrollment (
    student_id INTEGER NOT NULL,
    course_id INTEGER NOT NULL,
    PRIMARY KEY (student_id, course_id),
    FOREIGN KEY (student_id) REFERENCES student(id),
    FOREIGN KEY (course_id) REFERENCES course(id)
);

  1. What is the difference between a candidate key and a primary key?

Module 5 — Functional Dependencies & Normal Forms

Anomalies · 1NF · 2NF · 3NF · BCNF

▼

Functional Dependencies

A functional dependency X → Y states that in the relation, equal values of X imply equal values of Y. Dependencies describe domain rules and help identify keys and redundancy; they are not inferred safely from a small sample alone.

Anomalies and Normalization

Repeated facts can create update, insertion, and deletion anomalies. Normalization decomposes relations to reduce redundancy while preserving important dependencies where possible; joins may become necessary to reconstruct information.

FormInformal goal
1NFStore values in the chosen atomic domains; avoid repeating groups
2NFBe in 1NF and avoid non-prime attributes depending on only part of a candidate key
3NFBe in 2NF and avoid non-key transitive dependencies on a key
BCNFEvery nontrivial determinant is a superkey
Normalization is not simply “split every table.” Preserve keys and dependencies, understand the workload, and denormalize only for a measured reason with a consistency plan.

  1. Give an example of an update anomaly caused by storing a department name repeatedly with employee rows.
  2. What condition does BCNF impose on every determinant?

Module 6 — Transactions & ACID

Atomicity · Consistency · Isolation · Durability

▼

ACID Properties

A transaction is a logical unit of work. Atomicity treats its operations as all-or-nothing; consistency preserves declared invariants; isolation controls interactions among concurrent transactions; durability preserves committed effects according to the system's guarantees.

PropertyQuestion it answers
AtomicityDo all operations commit together or none?
ConsistencyAre constraints and invariants preserved?
IsolationHow do concurrent operations interact?
DurabilityDoes a committed result survive the specified failures?

Commit and Rollback

BEGIN;
UPDATE account SET balance = balance - 50 WHERE id = 1;
UPDATE account SET balance = balance + 50 WHERE id = 2;
COMMIT;

If a required step fails, the application should roll back the unit rather than leave a partial transfer. Actual syntax and guarantees vary by DBMS and configuration.

  1. Which ACID property prevents only one side of a transfer from being committed?
  2. Why should a transaction be kept no longer than necessary?

Module 7 — Concurrency Anomalies & Isolation

Dirty reads · Non-repeatable reads · Phantoms · Serializability

▼

Common Read Anomalies

Concurrent transactions can observe effects that are difficult to reason about. A dirty read observes uncommitted data; a non-repeatable read sees a changed value on rereading; a phantom occurs when a repeated predicate query returns a changed set of rows.

AnomalySketch
Dirty readT2 reads a value written by T1 before T1 commits
Non-repeatable readT1 reads a row, T2 changes and commits it, T1 rereads it
PhantomA repeated range query sees inserted/deleted matching rows
Lost updateConcurrent writes overwrite one another's intended change

Isolation Levels

Isolation levels trade concurrency against restrictions on observable anomalies. Names and exact behavior are defined by standards and DBMS implementations; snapshot isolation is useful but is not identical to serializable isolation in every system.

Never infer an isolation guarantee from its name alone. Check the DBMS documentation and test transaction behavior for the actual workload.

🏋️ Practice Questions

  1. Distinguish a dirty read from a non-repeatable read.
  2. Why can snapshot isolation still permit some non-serializable outcomes?

Module 8 — Locks, MVCC & Deadlocks

Two-phase locking · Versions · Conflict

▼

Lock-Based Control

Locks coordinate access to data. Shared locks generally allow compatible readers; exclusive locks protect writes. Two-phase locking grows a transaction's lock set before releasing locks and can ensure conflict serializability, but may block and deadlock.

Multi-Version Concurrency Control

MVCC keeps multiple row versions so readers can often observe a consistent snapshot while writers make changes. It can reduce reader-writer blocking but requires version cleanup and does not eliminate every conflict or anomaly.

Deadlocks

A deadlock occurs when transactions wait cyclically for resources held by one another. DBMSs may detect a cycle and abort a victim; applications should handle retryable transaction failures safely.

Module 9 — Logging, Checkpoints & Recovery

Write-ahead logging · Undo · Redo · Backups

▼

Write-Ahead Logging

Write-ahead logging records enough information to recover changes. The log must be persisted according to the system's write-ahead rule before corresponding data pages are considered safely written. Recovery may redo committed work and undo incomplete work, depending on the design.

MechanismPurpose
Log recordDescribes a change or transaction event
CheckpointLimits how far recovery must scan from a known state
RedoReapply changes that should be durable
UndoRemove effects of transactions that did not commit
BackupPreserve a recoverable copy at a point in time
Restore testVerify a backup can actually be used to recover service
Replication is not a backup by itself: accidental deletion or corruption can propagate. Test restore procedures and recovery-time objectives.

🏋️ Practice Questions

  1. Why does a write-ahead log need to reach durable storage before related data pages?
  2. What is the difference between making a backup and proving recoverability?

Module 10 — Storage Structures & Indexes

B-trees · Hash indexes · Selectivity · Write cost

▼

Index Basics

An index is an auxiliary structure that helps locate rows without scanning the whole table. B-tree indexes support ordered lookups and range scans; hash indexes are suited to equality lookups in systems that support them. Exact behavior and supported operators are DBMS-specific.

Index kindOften useful for
B-treeEquality, ordering, and range predicates
HashEquality predicates (where supported)
CompositeQueries filtering or ordering by a useful leading-column prefix
CoveringQueries whose needed columns can be served from the index

Index Trade-offs

Indexes consume storage and add work to inserts, updates, and deletes. Selectivity, table size, query shape, statistics, and write volume all matter; verify a query plan rather than adding every possible index.

Module 11 — Query Planning & Optimization

Parse · Plan · Execute · Statistics

▼

Query Processing Stages

A DBMS parses a query, validates names and types, rewrites or simplifies it, chooses a physical plan, then executes that plan. A logical expression can have multiple physical implementations with different costs.

Cost-Based Optimization

The optimizer estimates row counts and operation costs using statistics, indexes, constraints, and available operators. Stale statistics or skew can produce poor estimates, so inspect actual plans and measured row counts for expensive queries.

OperatorTypical role
Table scanRead rows from a table or storage structure
Index scanFind rows through an index
JoinCombine rows from related inputs
SortOrder rows for output or a downstream operator
AggregateCompute values per group or across rows

🏋️ Practice Questions

  1. Why can a selective predicate make an index scan more attractive than a table scan?
  2. Name one reason an estimated query plan may differ from actual performance.

Module 12 — Pages, Buffers & Physical Storage

Pages · Buffer pool · Row vs column stores

▼

Pages and Buffering

DBMSs commonly move data in pages or blocks between durable storage and memory. A buffer pool caches pages; locality and access patterns influence whether a workload benefits from sequential scans or indexed lookups.

Row-Oriented and Column-Oriented Storage

Row stores are often effective for transactional access to complete records. Column stores can be effective for analytical scans that read a few columns across many rows and compress similar values well. These are workload tendencies, not absolute rules.

  1. Why does reading one column from a wide analytical table often suit columnar storage?
  2. What does a buffer pool cache?

Module 13 — Replication, Sharding & Consistency

Availability · Partitioning · CAP context

▼

Replication and Sharding

Replication keeps copies of data across nodes for availability, read scaling, or disaster recovery; replicas may lag. Sharding partitions data across nodes and requires choosing a shard key, handling cross-shard work, and planning rebalancing.

TechniqueMain ideaTrade-off
ReplicationCopy data across nodesLag, conflict handling, and failover behavior
ShardingPartition records across nodesCross-partition queries and key hotspots
QuorumRequire a configured subset of replicas to respondLatency and availability trade-offs

CAP and Consistency

CAP describes trade-offs during a network partition: a distributed system cannot guarantee both linearizable consistency and availability for every request in that partition. It does not mean a system permanently chooses only two properties under normal operation; consistency models and failure assumptions matter.

  1. What operational problem can a poor shard key create?
  2. State CAP's trade-off specifically in the presence of a network partition.

Module 14 — Non-Relational Data Models

Key-value · Document · Wide-column · Graph

▼

NoSQL Families

NoSQL is a broad set of data models, not one database type. Choose according to access patterns, consistency needs, query flexibility, scale, operations, and data relationships rather than novelty.

ModelTypical shape
Key-valueLookup a value by a key
DocumentStore nested records queried by selected fields
Wide-columnOrganize sparse data by row keys and column families
GraphStore nodes and edges for relationship traversal

Relational and Non-Relational Choices

Relational systems offer expressive joins, constraints, and transactions across structured relations. Other models may simplify particular access patterns or horizontal scaling, but can move integrity and query complexity into application code. Polyglot persistence adds operational complexity and should solve a concrete need.

Module 15 — Access Control, Auditing & Availability

Least privilege · Encryption · Monitoring

▼

Security Controls

Use authenticated identities and least-privilege roles; separate administrative from application access; protect credentials; encrypt network traffic; audit sensitive operations; and validate inputs. Apply row- or column-level controls when the system and policy require them.

Operational Readiness

Plan capacity, patching, observability, failover, backup retention, restore tests, and incident response. Define recovery point and recovery time objectives with stakeholders and verify them through exercises.

Backups, replica failover, and encryption each address different risks. None replaces authorization, auditing, or tested recovery procedures.

🏋️ Practice Questions

  1. Explain least privilege for an application database account.
  2. What is the difference between a recovery point objective and a recovery time objective?

Module 16 — Database Design Case Study

Requirements · Grain · Keys · Workload

▼

A Practical Design Sequence

Clarify entities, workflows, data ownership, and invariants. Define each table's grain; choose candidate keys; model relationships and constraints; normalize to reduce anomalies; then identify real query and write patterns before selecting indexes or denormalization.

Review questionWhy it matters
What does one row represent?Prevents ambiguous facts and duplicate counting
Which key is stable?Supports references and safe updates
What must remain true?Guides constraints and transaction boundaries
Which reads and writes dominate?Informs indexes, partitioning, and storage decisions
How does failure recover?Validates logging, backups, and operational plans

Red Flags to Investigate

  • Repeated facts that cause update anomalies or conflicting values.
  • Missing key and foreign-key constraints that permit invalid states.
  • Long transactions or inconsistent lock order that increase contention or deadlocks.
  • Indexes added without a measured query plan or write-cost analysis.
  • Backups that have never been restored in a realistic environment.

🏋️ Practice Questions

  1. Design the main entities and keys for a small order-management system.
  2. For one important workflow, state its invariant, transaction boundary, and failure recovery.

DBMS Interview Questions & Answers

Modeling · Transactions · Indexes · Recovery · Distribution

▼

Q: What is the difference between a DBMS and a database?

A database is the organized data; the DBMS is the software that defines, stores, queries, protects, and recovers it. SQL is a query language commonly used with relational DBMSs, not the DBMS itself.

Q: What is a candidate key?

A candidate key is a minimal set of attributes that uniquely identifies each tuple. One candidate is selected as the primary key; other candidate keys remain alternate keys.

Q: What is a functional dependency?

X → Y means that within a relation, equal values of X determine equal values of Y. Functional dependencies express domain rules and help identify keys and normalization opportunities.

Q: Why normalize a relational schema?

Normalization reduces repeated facts and update, insertion, or deletion anomalies while structuring dependencies. It often requires joins to reconstruct information; any denormalization should address a measured workload need.

Q: What is the difference between 3NF and BCNF?

Informally, 3NF permits a nontrivial dependency when the determinant is a superkey or the dependent attribute is prime. BCNF requires every nontrivial determinant to be a superkey, so BCNF is stricter.

Q: Explain the ACID properties.

Atomicity is all-or-nothing execution; consistency preserves invariants; isolation controls concurrent interactions; durability preserves committed work under the system's stated failure guarantees.

Q: What is a dirty read?

A dirty read observes data written by a transaction that has not committed. If that transaction later rolls back, the reader has consumed a value that never became committed state.

Q: How does a non-repeatable read differ from a phantom?

A non-repeatable read observes a changed value when rereading the same row. A phantom occurs when repeating a predicate query returns a changed set of rows, such as after a matching row is inserted.

Q: What is serializability?

A schedule is serializable when its concurrent outcome is equivalent to some serial ordering of the transactions. Conflict serializability can be reasoned about using precedence constraints among conflicting operations.

Q: How does MVCC help with concurrency?

Multi-Version Concurrency Control maintains versions so readers can often see a consistent snapshot while writers proceed. It can reduce read/write blocking, but version retention and isolation semantics still require operational attention.

Q: What causes a deadlock, and how is it handled?

A deadlock occurs when transactions wait cyclically for locks or resources held by each other. A DBMS may detect the cycle and abort a victim; applications should handle retryable failures while keeping transactions safe to repeat.

Q: When would a B-tree index help?

It can help equality lookups, ordered scans, and range predicates when the indexed columns and query predicates align. It costs storage and adds maintenance work to writes, so inspect the actual query plan.

Q: What is a composite index's leading-column rule?

For a composite index on (a, b), queries constraining the leftmost column a can commonly use its ordered prefix. A predicate only on b may not benefit in the same way, depending on the DBMS and index type.

Q: What is write-ahead logging?

Write-ahead logging records change information durably before corresponding data pages are considered safely persisted. Recovery uses log records to redo committed work and undo incomplete work according to the DBMS design.

Q: Why is a checkpoint useful?

A checkpoint establishes a recovery reference point and can reduce how much log a system must process after a crash. It does not remove the need for logs or backups.

Q: What is the difference between replication and backup?

Replication maintains copies for availability or read scaling and may propagate accidental changes. A backup is a retained recovery copy; it must be protected and restoration must be tested.

Q: What does the CAP trade-off say?

In the presence of a network partition, a distributed system cannot guarantee both linearizable consistency and availability for every request. It is not a general claim that a system permanently chooses only two properties outside partitions.

Q: What is sharding, and what makes shard-key choice important?

Sharding partitions records across nodes. A good shard key distributes load while supporting common access patterns; a poor key can create hotspots or expensive cross-shard queries.

Q: When might a document database be a good fit?

It can fit access patterns centered on retrieving and updating nested, document-shaped records, especially when their structure is naturally aggregate-oriented. Consider consistency, indexing, relationship queries, and integrity needs before choosing it.

Q: What is the difference between RPO and RTO?

Recovery Point Objective is the maximum acceptable data loss measured in time; Recovery Time Objective is the target time to restore a service. Backups, logs, replication, and failover plans should be designed and tested against both.
