Module 1 — What Is Power BI? The Ecosystem

Desktop · Service · Mobile · Report Server

▼

🔶 Why Power BI exists

Power BI is Microsoft's business intelligence platform for connecting to data, transforming it, modeling relationships between tables, and turning the result into interactive reports and dashboards. The pitch over doing the same work in Excel is simple: a proper data model instead of scattered VLOOKUPs, a calculation engine (DAX) built for aggregating millions of rows instantly, and a sharing mechanism that gives everyone a live, governed view instead of emailed spreadsheet copies that go stale the moment someone edits their own.

The platform is not one application — it is four pieces that each do a different job, and most of the confusion new learners have ("where do I build this?") comes from not knowing which piece owns which step.

🧭 The four pieces of the ecosystem

  • Power BI Desktop — free Windows application. This is where you author: connect to sources, shape data in Power Query, build the model, write DAX, and design report pages.
  • Power BI Service (app.powerbi.com) — the cloud home. You publish finished .pbix files here, organize them into workspaces, package them into apps, schedule refreshes, and share with colleagues who never touch Desktop.
  • Power BI Mobile — iOS/Android apps for viewing published dashboards on the go, with natural-language Q&A and data alerts that push a notification when a KPI crosses a threshold.
  • Power BI Report Server — an on-premises alternative to the Service, for organizations that cannot put data in Microsoft's cloud (regulated industries, strict data-residency rules). It hosts .pbix reports on your own servers but lacks several Service-only features such as Q&A, dataflows, and automatic AI visuals.
ComponentRuns wherePrimary job
Power BI DesktopYour Windows machineAuthor reports and data models
Power BI ServiceMicrosoft cloudPublish, share, schedule refresh, collaborate
Power BI MobilePhone / tabletConsume dashboards, get alerts
Report ServerYour own serversOn-prem hosting when cloud isn't allowed

🔁 A typical end-to-end workflow

  1. Connect to one or more data sources in Desktop.
  2. Shape and clean the data in the Power Query Editor.
  3. Build the model: load tables, create relationships.
  4. Write DAX measures for the calculations the business actually asks for.
  5. Build report pages with visuals bound to those measures.
  6. Publish the .pbix to a workspace in the Service.
  7. Package into an app (or share the workspace directly) for your audience.
  8. Configure scheduled refresh so the published data stays current without manual re-publishing.

🏋️ Practice Questions

  1. List three reasons a shared Power BI report is more trustworthy than a shared Excel workbook for the same analysis.
  2. For a report that must stay fully on-premises for compliance reasons, which Power BI component would you deploy, and what capability would you lose compared to the Service?
🎤 One-Line Interview AnswerPower BI is an ecosystem, not a single tool: Desktop authors reports, the Service publishes and shares them, Mobile consumes them on the go, and Report Server hosts them on-premises when the cloud isn't an option.

Module 2 — Connecting to Data Sources

Excel · SQL Server · Web/API · Import vs DirectQuery

▼

🔗 Common source types

Power BI's Get Data dialog exposes well over a hundred connectors, but in daily analyst work a handful dominate: Excel workbooks and CSV files, folders full of files that need to be combined, relational databases (SQL Server, PostgreSQL, Oracle), web pages and REST APIs, SharePoint lists and document libraries, Dataverse, and SaaS connectors for tools like Salesforce or Google Analytics. Each connector exposes source-specific options (for SQL Server: server/database name and an optional native query; for Web: a URL and request headers) but they all funnel into the same Power Query Editor once the data lands.

⚖️ Import vs DirectQuery vs Live Connection

This is the first major architectural decision on any report, and it shapes everything downstream — refresh behavior, DAX capability, and performance.

ModeHow it worksStrengthTrade-off
ImportData is copied into Power BI's in-memory VertiPaq engineFastest queries, full DAX support, works offlineNeeds scheduled refresh; subject to model size limits
DirectQueryPower BI sends native queries to the source on every interactionAlways shows current source data, no duplicationSlower, limited DAX, puts load on the source system
Live ConnectionConnects to an existing Power BI dataset or Analysis Services modelReuses a certified model, no local copy at allNo local modeling — you inherit the remote model as-is

Import is the default choice for most reports because it is fast and gives you the complete DAX surface. DirectQuery earns its place when the source is too large to import, changes by the minute, or when governance requires a single live source of truth (e.g., a trading desk). Live Connection is specifically for building new reports on top of a dataset someone else already published and certified — you are not connecting to raw data at all, you are connecting to another Power BI (or SSAS) model.

🌐 Connecting to web and API sources

The Web connector accepts a URL and, for anything beyond a public unauthenticated endpoint, an authentication method: anonymous, Basic, Organizational Account, Web API key, or OAuth2 (handled via a custom connector or Azure AD app registration for most enterprise APIs). For paginated APIs you typically write a small M function that increments a page parameter and use List.Generate to call it until an empty page comes back — this is one of the few places where hand-written M is unavoidable even for business analysts.

🏋️ Practice Questions

  1. A sales manager wants a dashboard refreshed every 15 minutes against a 2-billion-row fact table that already lives in SQL Server. Which connection mode fits, and why would Import be the wrong call here?
  2. You need to connect to an internal REST API that requires an API key in a request header. Which connector would you start from, and what Power Query step lets you add that header?
🎤 One-Line Interview AnswerImport copies data into Power BI's in-memory engine for speed and full DAX support, DirectQuery queries the source live for freshness at the cost of speed and DAX limits, and Live Connection reuses someone else's already-published dataset instead of connecting to raw data at all — the choice depends on data volume, freshness needs, and whether a certified model already exists.

Module 3 — The Power Query Editor — Shaping Data

Applied Steps · Data types · Split columns · M language

▼

🧹 Applied Steps: a recorded, replayable recipe

Every click you make in the Power Query Editor — remove a column, rename a header, filter a row — is recorded as a step in the Applied Steps pane, in order, top to bottom. This is the single most important idea in Power Query: you are not editing a spreadsheet, you are building a recipe that gets replayed automatically every time the data refreshes. You can rename steps for clarity, reorder them (where it makes logical sense), insert a step in the middle, or delete one entirely, and the preview updates live so you can see the effect immediately.

✂️ Common shaping operations

  • Remove / choose columns — keep only what the model actually needs; narrower tables load faster and use less memory.
  • Rename columns — give them business-friendly names before they ever reach a report, so you're not renaming the same field in twenty visuals later.
  • Change data type — critical, not cosmetic. A date column left as text can't be used in time intelligence; a numeric column left as text won't aggregate; get this wrong early and every downstream measure misbehaves.
  • Split column — by delimiter (e.g., "Smith, John" → Last/First) or by fixed positions, useful for poorly structured source exports.
  • Filter rows — drop rows you don't want in the model at all (test records, future-dated placeholders, cancelled test orders).
  • Replace values / trim / clean — fix inconsistent casing, stray whitespace, and placeholder values like "N/A" before they pollute a grouping.

🔤 M, the language under the hood

Every single step in Applied Steps is really a line of M (Power Query's functional formula language), visible and editable in the Advanced Editor. The UI covers the vast majority of real shaping needs, but M is there for the rest: custom functions, conditional column logic too complex for the UI, or looping over a list of pages from an API. M is case-sensitive and functional — a query is literally one expression built from a chain of let ... in steps.

let
    Source = Csv.Document(File.Contents("C:\data\sales.csv"),
        [Delimiter=",", Columns=5, Encoding=1252]),
    #"Promoted Headers" = Table.PromoteHeaders(Source, [PromoteAllScalars=true]),
    #"Changed Type" = Table.TransformColumnTypes(#"Promoted Headers",
        {{"OrderDate", type date}, {"Amount", type number}})
in
    #"Changed Type"

🏋️ Practice Questions

  1. A source column named Amt_USD arrives as text with values like "1,204.50". List the Applied Steps, in order, you'd use to turn it into a usable numeric column.
  2. Why does changing a date column's data type early in the query matter for a measure that uses TOTALYTD later in the model?
🎤 One-Line Interview AnswerThe Power Query Editor records every shaping action as an ordered, replayable Applied Step written in the M language, so cleaning data once means it's cleaned automatically on every future refresh — data type correctness especially matters because it determines what DAX functions can legally operate on that column later.

Module 4 — Power Query — Combining Data

Merge · Append · Combine files from a folder

▼

🔀 Merge Queries — joining, Power Query's way

Merge works like a SQL join: it combines columns from two queries based on matching key columns, without stacking rows. You pick the two queries, the matching column(s) in each, and a join kind — Inner (only matches), Left Outer (all of the left, matches from the right), Right Outer, Full Outer, Left Anti (rows in the left with no match), or Right Anti. The result of a merge is a new column containing a nested table; you then expand the columns you actually need from it.

➕ Append Queries — stacking rows

Append is a union: it stacks the rows of two or more queries that share the same (or similar) columns into one table. The classic use case is combining twelve months of near-identical CSV exports — January_Sales.csv, February_Sales.csv, and so on — into a single Sales table. Column names don't have to match perfectly beforehand, but mismatched names produce extra columns with nulls, so renaming to a common schema first is standard practice.

OperationWhat it doesSQL equivalentWhen to use
MergeAdds columns from a second query based on a matching keyJOINEnriching a fact table with dimension attributes
AppendStacks rows from queries with a similar schemaUNION ALLCombining multiple files/periods into one table

📁 Handling multiple files or sheets at once

The Folder connector plus Combine Files automates the "append twelve CSVs" scenario: point it at a folder, Power Query samples one file, builds a transformation function from the steps you apply to that sample, and then applies that same function to every file in the folder automatically, appending the results. The same idea applies to a workbook with one sheet per month — use Excel.Workbook and expand each sheet, or use the folder pattern if each month is a separate file. New files dropped into the folder before the next refresh are picked up automatically with zero extra work.

🏋️ Practice Questions

  1. You receive a new CSV export every week with the same five columns. What Power Query feature avoids having to manually add each new file to your model by hand?
  2. You have a Customers table and an Orders table and need every order row to show the customer's region. Is this a Merge or an Append, and which join kind keeps orders even when a customer record is missing?
🎤 One-Line Interview AnswerMerge joins two queries side by side on a matching key like a SQL join, while Append stacks rows from similarly-shaped queries like a UNION ALL — and Combine Files from a folder automates append across any number of same-structured files so new files are picked up automatically on refresh.

Module 5 — Data Modeling Basics

Tables · Relationships · Star vs snowflake schema

▼

🏗️ Fact tables, dimension tables, and relationships

A Power BI model is a set of tables connected by relationships, not one giant flat table. Fact tables hold the events you measure — orders, transactions, clicks — and tend to be long and narrow with lots of rows and numeric measures. Dimension tables hold the descriptive context around those events — customers, products, dates, regions — and tend to be wide with fewer rows. A relationship links them through a shared key, typically the dimension's primary key to the fact table's corresponding foreign key, letting you slice fact data by any dimension attribute without duplicating that attribute into the fact table itself.

⭐ Star schema vs snowflake schema

A star schema puts one central fact table directly connected to fully denormalized dimension tables — a Date table, a Product table, a Customer table — each one hop away from the fact table, like points of a star. A snowflake schema takes it further: dimensions are normalized into sub-dimensions (e.g., Product splits into Product and ProductCategory), adding extra hops and extra joins.

AspectStar schemaSnowflake schema
Relationship hops to fact table12 or more
Query/DAX performanceFaster — fewer joins to resolveSlower — more relationships to traverse
DAX formula complexitySimpler, fewer ambiguous pathsMore complex, more room for filter-path ambiguity
StorageSome redundancy in wide dimension tablesLess redundancy, more normalized

Power BI's VertiPaq engine and DAX engine are both optimized for star schemas. Snowflaking saves some storage and mirrors how a transactional database is normalized, but it adds relationship hops that slow queries and make filter propagation harder to reason about. The standard recommendation — and the one Microsoft's own documentation pushes hard — is: flatten snowflaked dimensions into a star schema in Power Query before loading, even if that means some repeated text values in a wide dimension table.

🔗 One-to-many vs many-to-many

The overwhelmingly common relationship in a well-modeled star schema is one-to-many: one row in a dimension (one customer) relates to many rows in the fact table (many orders). Power BI auto-detects this and sets the dimension as the "one" side. Many-to-many relationships — e.g., a product can belong to multiple sales categories, and a category contains multiple products — are supported directly in modern Power BI but need extra care: they can produce ambiguous or inflated results if not thought through, and a bridge table that decomposes the many-to-many into two one-to-many relationships is often the safer, more transparent design.

🏋️ Practice Questions

  1. You inherit a model where Product is split into Product, ProductSubcategory, and ProductCategory tables, each with its own relationship. What would you do to it before building measures, and why?
  2. Describe, in your own words, why a fact table is typically the "many" side of a relationship with a dimension table.
🎤 One-Line Interview AnswerA Power BI model is a star schema of fact tables surrounded by denormalized dimension tables connected through one-to-many relationships; it's preferred over a snowflake schema because fewer relationship hops means faster queries, simpler DAX, and less ambiguity in how filters propagate.

Module 6 — Managing Relationships

Cardinality · Cross-filter direction · Active vs inactive

▼

🕸️ Cardinality

Every relationship in Power BI has a cardinality: one-to-many (the common case — one dimension row, many fact rows), many-to-one (the same relationship described from the other side), one-to-one (rare — two tables that share a unique key, essentially two halves of the same entity), or many-to-many (both sides can repeat). Power BI auto-detects cardinality when you create a relationship by dragging a field from one table onto another, but it's worth checking manually in the relationship's properties, especially after a schema change on the source — an unexpectedly duplicated key can silently flip an intended one-to-many into a many-to-many and throw off every downstream total.

↔️ Cross-filter direction

Cross-filter direction controls which way a filter applied on one table propagates to the other: Single means filters flow from the "one" side to the "many" side only (filtering Date filters Sales, but filtering Sales does not filter Date) — this is the default and correct choice for the vast majority of star-schema relationships. Both (bidirectional) lets filters flow in both directions, which sounds convenient but is the most common source of unexpected modeling bugs: it can create ambiguous filter paths when multiple bidirectional relationships intersect, and it measurably slows down query performance because the engine has more filter propagation paths to resolve on every query. Use Both deliberately, for specific many-to-many bridge-table scenarios, not as a default fix for "my slicer isn't filtering what I expected."

⏸️ Active vs inactive relationships

Only one relationship between any pair of tables can be active at a time — active relationships are drawn as a solid line in Model view and are the ones DAX uses automatically. If you need a second relationship path between the same two tables (a classic example: an Orders fact table with both an OrderDate and a ShipDate, each needing its own relationship to the Date table), only one can be active; the other is created as inactive (a dashed line) and has to be explicitly activated inside a specific measure using USERELATIONSHIP.

Sales by Ship Date =
CALCULATE (
    [Total Sales],
    USERELATIONSHIP ( Orders[ShipDate], 'Date'[Date] )
)

🏋️ Practice Questions

  1. A model has Sales connected to Date by OrderDate (active) and by DeliveryDate (inactive). Write the measure that totals sales by delivery date.
  2. A junior analyst sets a relationship to "Both" directions to fix a slicer that "wasn't working." What risk does that introduce, and what would you check first instead?
🎤 One-Line Interview AnswerRelationship cardinality defines how rows match between two tables, cross-filter direction defines which way filters propagate — single is the safe default and bidirectional should be deliberate, not a default fix — and only one relationship between two tables can be active at a time, with any extra path left inactive and activated per-measure via USERELATIONSHIP.

Module 7 — Introduction to DAX

Calculated columns vs measures · Evaluation timing

▼

🧮 What DAX is

DAX (Data Analysis Expressions) is the formula language used for calculations across Power BI, Excel's Power Pivot, and Analysis Services tabular models. It looks superficially like an Excel formula — functions, operators, references — but it operates on columns and tables inside a relational model, not on individual cells, and its behavior is governed by context: the same DAX expression can return a different number depending on what filters, slicers, or rows surround it when it's evaluated.

🆚 Calculated column vs measure — the critical distinction

This is the single most important conceptual split in DAX, and the one that trips up nearly every newcomer.

AspectCalculated columnMeasure
When it's computedAt data refresh / processing timeOn the fly, at query/visual render time
Where it livesStored physically in the model, row by rowNever stored — just a formula, computed on demand
Context it usesRow context (one row at a time)Filter context (whatever filters surround it: slicer, visual, page)
Can be used as a slicer/axis?Yes, like any normal columnNo — a measure only produces a value inside a visual
Memory costAdds to model size (compressed per column)Essentially free until evaluated
When to useNeed a static per-row value that behaves like a real column (e.g., a flag, a concatenated key)Nearly everything else — totals, ratios, YTD, anything that should react to what's on the report
Full Name =
Customers[FirstName] & " " & Customers[LastName]
Total Sales = SUM ( Sales[Amount] )

Full Name is a calculated column — it's a fixed, row-level value, stored once per customer, and could be dragged onto a visual as a label or slicer. Total Sales is a measure — it has no meaning on its own until a visual puts it inside a filter context (a specific region, a specific month), at which point it recalculates for exactly that context. The practical rule of thumb taught in every serious Power BI course: default to a measure; reach for a calculated column only when you genuinely need a static, row-level value that behaves like source data.

🏋️ Practice Questions

  1. You need a Profit Margin % that must always reflect whatever region and date range are currently filtered on the report. Should this be a calculated column or a measure, and why?
  2. You need a static Customer Tier label (Gold/Silver/Bronze) based on a customer's lifetime spend, used as a slicer. Why does that argue for a calculated column over a measure here?
🎤 One-Line Interview AnswerA calculated column is computed once per row at refresh time and stored in the model, usable like any ordinary column including as a slicer, while a measure is computed on demand at query time based on whatever filter context surrounds it and is never stored — the practical default is to use a measure for anything that should react to report interactions, and a calculated column only for static, row-level values.

Module 8 — Core DAX Functions

SUM · AVERAGE · COUNTROWS · DISTINCTCOUNT

▼

➕ The basic aggregation functions

Most measures in a real report are built from a small set of workhorse aggregation functions wrapping a single column:

Total Sales = SUM ( Sales[Amount] )
Average Order Value = AVERAGE ( Sales[Amount] )
Order Count = COUNTROWS ( Sales )
Distinct Customers = DISTINCTCOUNT ( Sales[CustomerID] )
Max Order = MAX ( Sales[Amount] )
Min Order = MIN ( Sales[Amount] )

Each of these is context-aware by nature — drop Total Sales onto a matrix with Region on rows and it recalculates per region automatically, with no extra code, because the surrounding filter context (one region at a time) is applied before the aggregation runs.

🔢 COUNTROWS vs DISTINCTCOUNT vs COUNT

COUNTROWS(Table) counts every row in a table regardless of column values — the most reliable way to count "how many orders," because it doesn't care whether any particular column has blanks. COUNT(Column) counts non-blank values in a specific column — it will under-count if that column has nulls. DISTINCTCOUNT(Column) counts the number of unique values in a column, the right choice for "how many distinct customers placed an order" as opposed to "how many order rows were placed."

Result
MeasureFormulaReturns for 500 orders, 120 unique customers, 3 orders missing a CustomerID
Order CountCOUNTROWS(Sales)500
Customers (COUNT)COUNT(Sales[CustomerID])497
Distinct CustomersDISTINCTCOUNT(Sales[CustomerID])120

🏋️ Practice Questions

  1. Why might COUNT(Sales[CustomerID]) and COUNTROWS(Sales) return different numbers on the same table?
  2. Write a measure that returns the number of distinct products sold, and explain why DISTINCTCOUNT is the right choice over COUNT.
🎤 One-Line Interview AnswerThe core DAX aggregations — SUM, AVERAGE, COUNTROWS, DISTINCTCOUNT — automatically recalculate for whatever filter context a visual applies, and the key distinction among the counting functions is that COUNTROWS counts table rows regardless of nulls, COUNT counts non-blank values in one column, and DISTINCTCOUNT counts unique values in that column.

Module 9 — CALCULATE and Filter Context

The most important DAX function · Modifying context

▼

🎯 Why CALCULATE is the most important function in DAX

CALCULATE evaluates an expression inside a modified filter context — it can add filters, remove filters, or replace filters that would otherwise apply. Almost every non-trivial DAX pattern — year-over-year comparisons, "percent of total," excluding a category, time intelligence — is built on top of CALCULATE, which is why it's often described as the single function that unlocks the rest of the language.

Sales Excl Returns =
CALCULATE (
    [Total Sales],
    Orders[Status] <> "Returned"
)

Here, [Total Sales] is evaluated not in whatever filter context the visual provides, but in that context further restricted by Orders[Status] <> "Returned" — regardless of what's already filtered on the report, returned orders are excluded from this specific measure.

🧠 Row context vs filter context

Row context exists wherever DAX is evaluating one row at a time — inside a calculated column, or inside an iterator function like SUMX. It has no awareness of filters; it just knows "the current row." Filter context is the set of filters currently in effect from slicers, visual axes, page filters, and other measures wrapping the current one — it's what determines which rows are visible to an aggregation like SUM. CALCULATE is the primary tool for manipulating filter context, and it's also the mechanism that converts row context into filter context when needed (a subtlety called context transition, which happens automatically whenever CALCULATE is used inside a row context, such as inside a calculated column).

🔍 Worked example: percent of total

A classic use of CALCULATE with ALL to remove filters rather than add them:

% of Total Sales =
DIVIDE (
    [Total Sales],
    CALCULATE ( [Total Sales], ALL ( Products ) )
)

ALL(Products) strips any filters coming from the Products table, so the denominator is always the grand total sales regardless of which product category the visual is currently sliced to — giving each row its true percentage of the whole, not of its own sub-total.

🏋️ Practice Questions

  1. Write a measure for Sales This Year Excluding Discounted Items, excluding any row where Orders[IsDiscounted] = TRUE().
  2. Explain, in one or two sentences, why [Total Sales] alone inside a product-category visual gives a different number than CALCULATE([Total Sales], ALL(Products)) in the same cell.
🎤 One-Line Interview AnswerCALCULATE is the engine of DAX because it lets you evaluate any expression inside a deliberately modified filter context — adding, removing, or replacing filters — and it's also what converts row context into filter context, which is why nearly every advanced DAX pattern, from percent-of-total to time intelligence, is built directly on top of it.

Module 10 — Time Intelligence in DAX

Date tables · TOTALYTD · SAMEPERIODLASTYEAR

▼

📅 Why you need a dedicated date table

Every DAX time-intelligence function — year-to-date, same period last year, month-over-month — relies on a continuous, unbroken date table marked as such (Model view → table → "Mark as Date Table") and related to the relevant fact table(s) on a date key. "Continuous" means every calendar date in the relevant range exists as a row, even dates with no transactions — skip a date and time-intelligence functions can silently miscalculate because they rely on contiguous date ranges to find "the same date last year" or "the first day of the fiscal year."

⏳ TOTALYTD and SAMEPERIODLASTYEAR

Sales YTD =
TOTALYTD ( [Total Sales], 'Date'[Date] )

Sales LY =
CALCULATE ( [Total Sales], SAMEPERIODLASTYEAR ( 'Date'[Date] ) )

YoY Growth % =
DIVIDE ( [Total Sales] - [Sales LY], [Sales LY] )

TOTALYTD is shorthand for a CALCULATE with a year-to-date date filter baked in; SAMEPERIODLASTYEAR shifts the current date filter back exactly one year, which CALCULATE then applies — both depend entirely on the Date table being marked and properly related, otherwise they either error or silently return wrong totals.

📈 Other common time intelligence functions

DATEADD('Date'[Date], -1, MONTH) shifts the current period by an arbitrary interval; PREVIOUSMONTH/PREVIOUSQUARTER/PREVIOUSYEAR return the prior period directly; PARALLELPERIOD is useful for fiscal-year comparisons that don't align with calendar years. All of them share the same prerequisite — a clean, continuous, marked date table — which is why setting one up is usually the very first modeling step on any new Power BI file, before a single measure is written.

🏋️ Practice Questions

  1. A finance team's fiscal year starts in April, not January. What would you need in your date table to support TOTALYTD against their fiscal calendar?
  2. A Sales YTD measure returns blank for every row after you add a new year's data. What's the most likely cause given what the date table needs?
🎤 One-Line Interview AnswerTime intelligence functions like TOTALYTD and SAMEPERIODLASTYEAR are really CALCULATE with a specific date filter pattern built in, and every one of them depends on a continuous, explicitly marked date table properly related to the fact table — without that, they either throw errors or quietly compute the wrong period.

Module 11 — Building Visuals

Bar · Line · Card · Table · Matrix

▼

🖼️ Matching visual type to the question being asked

Every visual type answers a different kind of question, and picking the wrong one is the most common beginner report-design mistake.

Question being askedBest visualWhy
"How do categories compare?"Bar / column chartLength is the easiest visual comparison for the eye
"How did this change over time?"Line chartTrend and slope are immediately visible
"What's the single current number?"CardNo chart needed — just the number
"What share does each part have?"Bar chart (stacked sparingly) or donut for 2-4 slicesPie/donut charts degrade fast past a handful of categories
"I need the exact numbers, not just a shape"Table / matrixPrecise values, sortable, supports subtotals and drill-down

🎯 Choosing the right visual, and common mistakes

Pie and donut charts are frequently overused for comparisons they're bad at — once you're past four or five slices, a bar chart reads faster and more accurately, because humans compare lengths far better than angles. 3-D variants of any chart type add visual noise without adding information and are generally avoided entirely in professional report design. A matrix (as opposed to a flat table) earns its place whenever the audience needs row/column cross-tabulation with subtotals and the ability to expand/collapse hierarchy levels — e.g., Year → Quarter → Month down the rows, Region across the columns.

🏋️ Practice Questions

  1. A stakeholder wants to compare revenue across 9 product categories for one month. Which visual would you push back against, and which would you propose instead?
  2. Design a single KPI card plus supporting visual combination for "are we on pace to hit this quarter's revenue target," and justify each visual choice.
🎤 One-Line Interview AnswerVisual choice should follow the question, not habit: bars for comparing categories, lines for trends over time, cards for single current numbers, and tables or matrices when the audience needs precise, cross-tabulated figures rather than a shape — and pie charts in particular should be reserved for a very small number of slices.

Module 12 — Slicers, Filters & Drill-Through

Filter scopes · Sync slicers · Drill-through pages

▼

🔍 The three filter scopes

Power BI applies filters at three nested scopes, each one only able to further restrict what's already visible: visual-level filters apply to a single visual only; page-level filters apply to every visual on that page; report-level filters apply to every page in the entire report. When debugging "why is this number wrong," checking all three scopes, top to bottom, is the standard first move — a report-level filter silently narrowing everything is a common surprise for someone only looking at the visual-level filter pane.

🎚️ Slicers vs the Filters pane

A slicer is a visual, interactive, on-canvas control — a list, dropdown, date range, or button set the report viewer can click directly, and its state is visible at a glance to anyone reading the page. The Filters pane achieves the same filtering effect but lives in a side panel that's less prominent (and can be hidden from viewers entirely), making it better suited for filters the report author wants applied but doesn't need the audience to actively manipulate. Slicers can be synced across multiple pages via the Sync Slicers pane, so selecting "2026" on page one carries that selection to every other synced page without the slicer even needing to be visible there.

🕳️ Drill-through pages

A drill-through page is a detail page a viewer reaches by right-clicking a data point on a summary visual and selecting "Drill through," landing on a page pre-filtered to exactly that context (e.g., right-click a region on a summary map, drill through to an order-detail page already filtered to that region). It's set up by dragging a field into the Drill through well of the target page; a back button is added automatically so the viewer can return to the summary page. This pattern keeps a dashboard's main pages clean and high-level while still giving power users a path to transaction-level detail without cluttering the summary with every possible field.

🏋️ Practice Questions

  1. A report has a report-level filter restricting Year = 2026, but a specific visual still needs to show all years. Which filter scope would you use to override that, and is it even possible given the report-level filter?
  2. Design a drill-through flow from a regional sales summary page to an order-detail page, naming the field you'd use as the drill-through filter.
🎤 One-Line Interview AnswerFilters apply at three nested scopes — visual, page, and report — each narrowing further; slicers are the on-canvas, viewer-facing way to filter interactively (optionally synced across pages), while drill-through pages let a viewer jump from a summary data point straight to a pre-filtered detail page without cluttering the main report.

Module 13 — Formatting & Report Design

Themes · Conditional formatting · Tooltips · Clarity over decoration

▼

🎨 Themes for consistency

A Power BI theme (a JSON file, or one of the built-in palettes) fixes the color palette, fonts, and default visual styling across the entire report in one place, instead of manually color-matching every visual by hand. Organizations typically ship a branded theme file so every report an analyst publishes automatically uses the company's brand colors without anyone having to remember a hex code.

🚦 Conditional formatting

Conditional formatting applies rules-based styling directly to table/matrix cells or card values — color scales (a gradient from red to green based on value), data bars (an in-cell bar proportional to the value), or custom rules (e.g., red text when a KPI misses target). This turns a flat table of numbers into something a viewer can scan in two seconds instead of reading row by row.

💬 Tooltips

The default tooltip shows the underlying data point's values on hover. A report-page tooltip is a small custom report page — built like any other page but set as a tooltip — that appears on hover instead, letting you show a mini chart, a sparkline, or several extra metrics for the hovered point without needing a drill-through click.

✅ Designing for clarity over decoration

The strongest report-design instinct to build early: every element on the page should earn its place by adding information, not visual interest. Practical rules that hold up across most professional dashboards — align visuals to a consistent grid, don't mix more than two or three chart types on one page, title visuals with what the number means ("Revenue is 12% behind target" beats "Revenue"), and resist adding a visual just because there's empty space left on the canvas.

🏋️ Practice Questions

  1. A report has five different accent colors used inconsistently across its eight pages. What single artifact would fix this in one step, applied once?
  2. Propose a conditional formatting rule for an "Orders Past Due" table that should visually flag rows more than 30 days overdue.
🎤 One-Line Interview AnswerGood Power BI formatting is about consistency and signal: a shared theme keeps colors and fonts uniform without manual work, conditional formatting lets a viewer spot outliers at a glance instead of reading every cell, and the overriding design principle is that every visual on the page should earn its place by adding information rather than decoration.

Module 14 — Publishing & the Power BI Service

Publish · Workspaces · Apps · Sharing

▼

🚀 Publishing a report

From Power BI Desktop, the Publish button sends the .pbix file — both its dataset and its report pages — to a chosen workspace in the Power BI Service. From that point on, the dataset and the report exist as separate objects in the Service: the dataset can be reused by other reports, and the report can be viewed, further duplicated, or embedded, independent of the original Desktop file.

🗂️ Workspaces

A workspace is a container in the Service that groups related datasets, reports, dashboards, and dataflows — typically scoped to a team or a subject area ("Sales Analytics," "Finance Ops"). Workspace access is role-based: Admin (full control, including workspace settings and membership), Member (can publish and edit content), Contributor (can edit but not publish an app or manage access), and Viewer (read-only). Choosing the right workspace, and the right role for each collaborator, is the first line of governance for who can change what.

📦 Apps

An app is a curated, read-only, versioned package built from one or more reports/dashboards in a workspace, distributed to a broad audience who never need edit access to the underlying workspace. The author controls what's included and when a new version goes out, so business users always see a stable, intentional view — separating "where the content is built and edited" (the workspace) from "what end users actually see" (the app) is a core governance pattern in any organization with more than a handful of report consumers.

🏋️ Practice Questions

  1. A finance team edits reports daily, but 200 executives across the company should only ever see the latest finished version. What two Service constructs would you use together, and what does each one solve?
  2. What workspace role would you assign to a contractor who should be able to edit report visuals but shouldn't be able to publish an app or change workspace membership?
🎤 One-Line Interview AnswerPublishing sends a Desktop report's dataset and pages to a workspace in the Power BI Service; workspaces are role-gated containers for building and collaborating on content, while an app is the separate, curated, read-only package that distributes a stable version of that content to a broad audience without giving them edit access.

Module 15 — Refresh & Gateways

Scheduled refresh · On-premises data gateway · Troubleshooting

▼

🔄 Scheduled refresh

A published Import-mode dataset only stays current if it's refreshed — scheduled refresh, configured in the dataset's settings in the Service, re-runs every Power Query step and reloads the model automatically on a defined cadence. Power BI Pro licenses allow up to 8 scheduled refreshes per day per dataset; Premium capacity raises that ceiling to 48 per day, reflecting its higher compute allocation. DirectQuery datasets don't need this at all, since every query already hits the live source.

🌉 The on-premises data gateway

When a dataset's source lives behind a corporate firewall — an on-prem SQL Server, a file share, an on-prem SSAS model — the Power BI Service has no direct network path to reach it. The on-premises data gateway is a small Windows service installed inside that network boundary that relays queries from the cloud Service to the local source securely. There are two gateway modes: the Personal gateway (single user, Import-only refresh, no sharing of the connection), and the Standard/Enterprise gateway (installed by IT, shared across the organization, supports DirectQuery and Live Connection in addition to scheduled Import refresh, and supports high-availability clustering).

🛠️ Troubleshooting refresh failures

The most common causes, roughly in order of frequency: expired or changed credentials on the data source connection (a password rotation breaks the stored credential silently until the next refresh attempt); a schema change at the source that breaks a Power Query step expecting a column that no longer exists or was renamed; the gateway being offline or unreachable; and source timeouts on very large or slow queries exceeding the refresh time limit. The dataset's Refresh history in the Service shows the exact error message and timestamp for each failed attempt, which is always the first place to look rather than guessing.

🏋️ Practice Questions

  1. A scheduled refresh has failed every night for a week with no report changes made. What are the first two things you'd check, in order?
  2. A source database lives entirely inside a corporate network with no public endpoint. What component is required before scheduled refresh can even be configured in the Service?
🎤 One-Line Interview AnswerScheduled refresh keeps an Import-mode dataset current on a defined cadence — up to 8 times a day on Pro, 48 on Premium — and when the source sits behind a firewall, an on-premises data gateway relays those queries securely into the network; most refresh failures trace back to expired credentials or a schema change at the source, both visible in the dataset's refresh history.

Module 16 — Row-Level Security & Governance

RLS roles · Why it matters · Certification

▼

🔐 What Row-Level Security does

Row-Level Security (RLS) restricts which rows of data a given user can see, inside the exact same published report and dataset everyone else uses — there is one dataset, not one copy per region or client, and RLS filters it dynamically based on who's viewing. It's implemented in Desktop under Modeling → Manage Roles: you define a role (e.g., "Region Manager") and attach a DAX filter expression to a table that restricts visible rows for anyone in that role.

[Region] = LOOKUPVALUE (
    UserRegionMap[Region],
    UserRegionMap[UserEmail], USERPRINCIPALNAME()
)

That expression, attached to a Sales or Region table's role filter, looks up the signed-in user's email via USERPRINCIPALNAME() against a mapping table and only allows rows matching their assigned region. After defining a role, View As Role inside Desktop lets you test it before publishing, and in the Service, users (or Azure AD security groups) are assigned to that role on the dataset's security settings.

🧾 Why it matters for shared dashboards

Without RLS, "one dataset, many viewers" means everyone sees everything — fine for a small team, unacceptable the moment a dashboard spans multiple regional sales teams, client-facing portals, or any scenario where one viewer legitimately should not see another's data. RLS is what makes "publish once, one source of truth" compatible with "different people are allowed to see different slices of it," instead of forcing you to maintain parallel reports per audience.

✅ Dataset certification and governance

Larger organizations use endorsement: a dataset can be marked Promoted (the owning team vouches for it informally) or Certified (passed a formal governance review, typically restricted to designated certifying users) — certified datasets are visually flagged and surfaced higher in search, signaling to the whole organization "build on this one, it's trustworthy," rather than everyone re-building a near-duplicate version of the same numbers. Combined with lineage view (which traces a dataset back through its sources and forward through every report built on it), this is how an organization keeps a sprawling library of reports from drifting into inconsistent, duplicated metrics.

🏋️ Practice Questions

  1. A single sales dataset needs to be shared with three regional VPs, each of whom should only see their own region's numbers. Describe the RLS setup, start to finish.
  2. Explain, to a skeptical manager, why certifying one dataset as the "source of truth" for revenue reduces organizational risk compared to letting every team build its own.
🎤 One-Line Interview AnswerRow-Level Security filters a single shared dataset differently per viewer using a DAX role filter tied to the signed-in user, so one dataset can safely serve audiences who shouldn't see each other's data; at an organizational level, certifying trusted datasets and tracking lineage is what keeps dozens of reports from drifting into inconsistent, duplicated versions of the same numbers.

Module 17 — Performance Best Practices

Model size · Bidirectional relationships · DirectQuery · Visual overuse

▼

⚡ Reduce model size first

Most performance problems start with an oversized model, and the fixes are mostly subtractive: remove columns nothing references, prefer measures over calculated columns wherever possible (calculated columns are stored and compressed per-column, so an unnecessary one is pure waste), use integer surrogate keys for relationships instead of long text keys (integers compress and join far more efficiently in VertiPaq), disable Auto date/time for tables that don't need it (it silently creates a hidden date table per date column, multiplying model size fast), and load data at the grain the business actually needs rather than always importing the finest possible detail.

↔️ Avoid unnecessary bidirectional relationships

As covered in relationship management, a bidirectional (both-direction) relationship lets filters flow both ways between two tables — but every bidirectional relationship is an extra path the DAX engine has to consider when resolving a query, and stacking several of them can create genuinely ambiguous filter propagation. The performance guidance is blunt: default every relationship to single-direction, and only flip to bidirectional for a specific, understood many-to-many scenario — never as a generic fix for a slicer that "isn't filtering right."

🐢 DirectQuery performance considerations

Because DirectQuery sends a live query to the source for essentially every visual interaction (a slicer click, a filter change), performance is bounded by the source system's query speed, not Power BI's own engine — a report that feels instant in Import mode can feel sluggish in DirectQuery against the exact same data. The aggregations feature mitigates this: a smaller, pre-summarized Import table serves high-level queries instantly, while the engine only drops down to DirectQuery detail when a query needs row-level granularity the aggregation can't answer.

🧹 Avoid filter and visual overuse

A report page packed with fifteen visuals, each carrying several of its own visual-level filters, forces the engine to resolve that many separate queries on every page load and every slicer click — the perceived slowness users complain about is very often this, not the model itself. Power BI's built-in Performance Analyzer (View → Performance Analyzer) records exactly how long each visual took to render and how much of that was the DAX query versus visual rendering, and is the correct first diagnostic step before guessing at a fix.

🏋️ Practice Questions

  1. A report feels slow specifically in DirectQuery mode but was fast when prototyped against a small sample in Import mode. What's the most likely explanation, and what feature could help without abandoning DirectQuery entirely?
  2. Name three concrete changes you'd check for first when asked to speed up a sluggish Power BI report, and the tool you'd use to confirm where the time is actually going.
🎤 One-Line Interview AnswerPower BI performance work starts with shrinking the model — fewer unused columns, measures over calculated columns, integer keys, auto date/time off — then auditing relationships for unnecessary bidirectional paths, considering aggregations if DirectQuery feels slow, and using the built-in Performance Analyzer to find out exactly which visual or query is actually the bottleneck rather than guessing.

Module 18 — Interview Questions

Ecosystem · Modeling · DAX · Governance · Performance

▼

Q: What's the difference between Power BI Desktop and Power BI Service?

Desktop is the free Windows authoring tool where you connect to data, build the model, write DAX, and design report pages — it's where the .pbix file is actually built. The Service is the cloud platform where finished reports get published, organized into workspaces, packaged into apps, shared with colleagues, and kept current through scheduled refresh. You can view a published report in a browser without ever installing Desktop, but you can't build or edit the underlying model from the Service alone — editing a dataset still typically routes back through Desktop.

Q: When would you choose DirectQuery over Import, and what do you give up?

I'd choose DirectQuery when the source is too large to realistically import, when the business genuinely needs to-the-minute freshness rather than scheduled refresh, or when governance requires a single live source of truth that can't be duplicated. What you give up is speed — every interaction fires a live query against the source — and a chunk of the DAX surface, since several functions and patterns that work fine against an in-memory Import model aren't supported or perform poorly against a live source. My default is still Import; I only reach for DirectQuery when a specific constraint rules it out.

Q: Explain the difference between a calculated column and a measure.

A calculated column is computed once per row at refresh time and physically stored in the model, so it behaves like any other column — you can use it as a slicer, an axis, or a filter, and it costs memory. A measure has no stored value at all; it's a formula evaluated on demand based on whatever filter context a visual provides, which is what lets the same measure return a different number in every cell of a matrix. My rule of thumb is to default to a measure for anything that should react to the report, and only use a calculated column when I need a genuinely static, row-level value like a concatenated key or a fixed tier label.

Q: Why is star schema preferred over snowflake schema in Power BI?

A star schema connects every dimension directly to the fact table in one hop, which is exactly what Power BI's VertiPaq and DAX engines are optimized for — fewer relationship hops means faster queries and far less ambiguity about how a filter propagates. A snowflake schema normalizes dimensions further, adding extra joins that slow things down and complicate DAX. The trade-off is some redundant text storage in a wider dimension table, but that's cheap compared to the performance and simplicity gained, so in practice I flatten snowflaked sources into a star schema in Power Query before ever loading the model.

Q: What is CALCULATE and why do people call it the most important function in DAX?

CALCULATE evaluates an expression inside a modified filter context — it can add, remove, or replace the filters that would otherwise apply. It's foundational because nearly every advanced DAX pattern is really CALCULATE under a different name: TOTALYTD and SAMEPERIODLASTYEAR are CALCULATE with a specific date filter baked in, percent-of-total patterns use CALCULATE with ALL to strip filters, and context transition — turning row context into filter context inside a calculated column — happens specifically because CALCULATE is invoked. Once you genuinely understand CALCULATE, most of the rest of DAX is pattern recognition on top of it.

Q: What's the difference between row context and filter context?

Row context is what exists when DAX is evaluating one row at a time, like inside a calculated column or an iterator such as SUMX — it knows "the current row" and nothing about surrounding filters. Filter context is the set of filters currently in effect from slicers, page filters, visual axes, and wrapping measures, and it's what an aggregation like SUM actually respects when it decides which rows to include. The subtlety worth knowing cold for an interview is context transition: wrapping an expression in CALCULATE inside a row context converts that row into an equivalent filter, which is how a calculated column can call a measure and get a row-specific result.

Q: What is relationship cardinality and why does it matter?

Cardinality describes how rows on each side of a relationship match up — one-to-many is the standard case in a star schema, with a dimension's unique key on the "one" side and a fact table's repeating foreign key on the "many" side. It matters because getting it wrong changes how numbers aggregate: if a key you assumed was unique on the dimension side actually has duplicates, the relationship silently becomes many-to-many and totals can double-count. I always verify cardinality explicitly after any schema change at the source rather than trusting the auto-detected setting indefinitely.

Q: When do you need a many-to-many relationship, and how do you handle it safely?

I need one when neither side of a relationship is naturally unique — for example, a product can belong to multiple sales categories and a category contains multiple products. Power BI supports many-to-many relationships directly now, but I still prefer decomposing it into a bridge table with two clean one-to-many relationships wherever possible, because it's far easier to reason about and debug than a direct many-to-many link, which can produce inflated or ambiguous totals if the data isn't exactly as clean as assumed.

Q: What's Row-Level Security and how do you implement it?

RLS restricts which rows of a single shared dataset a given user is allowed to see, based on their identity, rather than maintaining separate datasets per audience. I implement it in Desktop under Manage Roles, writing a DAX filter expression — often a LOOKUPVALUE against a user-to-region mapping table filtered by USERPRINCIPALNAME() — then test it with View As Role before publishing, and finally assign actual users or Azure AD groups to that role on the published dataset in the Service. It matters most the moment a single dashboard serves audiences who legitimately shouldn't see each other's data, like multiple regional managers or external clients.

Q: How do you schedule a dataset refresh, and what are the limits?

Scheduled refresh is configured on the dataset in the Power BI Service, under its settings, where you set a time zone and one or more times per day. Power BI Pro allows up to 8 scheduled refreshes per day per dataset, while Premium capacity raises that to 48 per day, reflecting the extra compute Premium reserves. DirectQuery datasets don't need scheduled refresh at all since every query already reads live from the source — the setting is specific to Import-mode datasets.

Q: What's an on-premises data gateway and when do you need one?

It's a small Windows service installed inside a network boundary that relays queries from the cloud-based Power BI Service to a data source the Service can't reach directly, like an on-prem SQL Server or a file share behind a firewall. I'd need one any time a source isn't reachable over the public internet. There's a Personal gateway for single-user Import-only scenarios and a Standard/Enterprise gateway, installed and managed by IT, that's shared across the organization and additionally supports DirectQuery and Live Connection, plus clustering for high availability.

Q: What's the difference between slicers and filters?

Both restrict visible data, but a slicer is an on-canvas, interactive visual the report viewer can click directly — a dropdown, a list, a date range — with its current selection always visible on the page. A filter, applied through the Filters pane, achieves the same restriction but lives in a side panel that can be hidden from the audience entirely, which makes it better suited to constraints the author wants enforced without the viewer needing to actively control them. Slicers can also be synced across multiple report pages so one selection carries everywhere.

Q: When would you use Power Query instead of DAX for a transformation?

Power Query is the right tool for anything that's really data cleaning or restructuring — changing data types, splitting or merging columns, filtering out bad rows, combining multiple files, reshaping a pivoted export into a proper table — because those operations happen once at refresh time and the result is stored, which is cheaper and simpler than recomputing it on every query. DAX is for calculations that need to react to the current filter context at query time — totals, ratios, time intelligence. My rule: if the result should be the same for everyone looking at the report, it almost always belongs in Power Query; if it should change depending on what's selected, it belongs in DAX.

Q: What's a bidirectional relationship and why is it risky?

It's a relationship set to filter in both directions instead of only from the "one" side to the "many" side. It's risky because stacking multiple bidirectional relationships across a model can create ambiguous filter paths the engine has to resolve, producing results that are hard to reason about, and it measurably slows query performance even when it works correctly. I default every relationship to single-direction and only turn one bidirectional for a specific, well-understood scenario, usually a many-to-many bridge table, never as a generic fix for a filter that isn't behaving as expected.

Q: A report is slow. Walk me through how you'd approach fixing it.

I'd start with Performance Analyzer to find out exactly which visual and which part of its query — the DAX engine versus the rendering — is actually slow, rather than guessing. From there I'd check the usual suspects in order: an oversized model carrying unused columns or calculated columns that should be measures, unnecessary bidirectional relationships adding ambiguous filter paths, DirectQuery mode against a slow source with no aggregations layer, or simply too many visuals and visual-level filters on one page forcing too many simultaneous queries. I fix the biggest confirmed bottleneck first and re-measure rather than changing several things at once.

Q: Why do time intelligence functions require a date table, and what makes a date table valid for that purpose?

Functions like TOTALYTD and SAMEPERIODLASTYEAR work by shifting or bounding a date filter internally, and that logic assumes a continuous, unbroken sequence of calendar dates to shift across — skip dates and "the same date last year" may not resolve correctly. A valid date table has one row per calendar day with no gaps across the full range the data needs, is explicitly marked as a date table in Model view, and is properly related to the fact table on a true date-typed key column, not a text or integer surrogate.

Q: What's the difference between a Power BI app and a workspace?

A workspace is where content is actually built and collaborated on — datasets, reports, and dashboards live there, and access is role-based (Admin, Member, Contributor, Viewer) for people who need to edit. An app is a separate, curated, read-only, versioned package built from content in a workspace and distributed to a broad audience who never need edit access at all. Separating the two means the authoring team can iterate freely in the workspace while business users always see a stable, intentional version through the app, with no risk of catching a report mid-edit.

  2. Write one additional interview question an interviewer might ask about Power BI governance that isn't covered above, and answer it in the same style.
🎤 One-Line Interview AnswerThese are the questions that come up most often in real Power BI interviews — the common thread across nearly all of them is understanding context: filter context versus row context, when a filter should flow versus stay put, and when a transformation belongs in Power Query versus DAX.

🗺️ A staged path from zero to production
