Module 1 — Object-Oriented Thinking

State · Behavior · Responsibilities

▼

What Is Object-Oriented Programming?

Object-oriented programming organizes software around objects that hold state and expose behavior. A class describes a family of objects; an object is a particular instance. OOP is a set of design tools, not a requirement to model every function or value as a class.

ConceptMeaning
ObjectAn identity-bearing entity with state and behavior
ClassA definition for creating objects with shared structure or behavior
StateData that describes an object's current condition
BehaviorOperations the object supports
InterfaceThe operations and guarantees visible to a caller

Four Common OOP Ideas

Encapsulation groups state and behavior behind a boundary. Abstraction exposes useful behavior while hiding implementation details. Inheritance derives a specialized type from a base type. Polymorphism lets callers use different implementations through a shared contract.

These ideas are useful when they reduce complexity or clarify ownership; procedural and functional designs remain appropriate for many tasks.

Module 2 — Classes, Instances & Identity

Construction · Attributes · Methods

▼

Define a Class and Create an Instance

A class defines behavior and may define the data each instance owns. Calling a constructor creates or initializes an instance; two instances of the same class can have different state and distinct identity.

class Account:
    def __init__(self, owner):
        self.owner = owner
        self.balance = 0

    def deposit(self, amount):
        self.balance += amount

first = Account("Mina")
second = Account("Ravi")

first and second are distinct objects even though both are instances of Account. Keep creation syntax separate from the object's public behavior when callers do not need to know implementation details.

Identity and Equality

Identity asks whether two references point to the same object. Equality asks whether two values should be considered equivalent according to a defined contract. A value object may compare by its fields; an entity often retains identity as it changes.

🏋️ Practice Questions

  1. Can two accounts have the same class but different balances?
  2. Explain the difference between object identity and value equality.

Module 3 — Encapsulation & Invariants

Boundaries · Validation · Controlled mutation

▼

Protect Valid State

Encapsulation means callers interact through an intentional interface rather than freely changing implementation details. An invariant is a condition that should remain true, such as a nonnegative account balance or an order containing at least one line item.

class Account:
    def __init__(self, owner):
        self.owner = owner
        self._balance = 0

    @property
    def balance(self):
        return self._balance

    def deposit(self, amount):
        if amount <= 0:
            raise ValueError("amount must be positive")
        self._balance += amount

Python's underscore is a convention, not access control enforced by the runtime. In languages with visibility modifiers, use them to express the intended API. Validate at the boundary where the invariant can be enforced reliably.

🏋️ Practice Questions

  1. State one invariant for a shopping cart.
  2. Why is a controlled method safer than letting every caller update a balance directly?

Module 4 — Abstraction & Contracts

Hide detail · Expose guarantees

▼

Abstraction

An abstraction exposes what a caller can do and the guarantees it receives, without requiring knowledge of how the work is implemented. A repository interface can hide whether data comes from a database, memory, or a remote service.

class MessageSender:
    def send(self, recipient, message):
        raise NotImplementedError

def notify(sender, recipient, message):
    sender.send(recipient, message)

The notify function depends on a small contract instead of a specific email provider. Good abstractions are shaped by stable client needs; speculative layers can make simple code harder to understand.

🏋️ Practice Questions

  1. What should a caller know about an abstraction?
  2. Name two implementations that could satisfy a message-sending interface.

Module 5 — Inheritance & Substitutability

Base types · Overrides · Contracts

▼

Inheritance

Inheritance defines a subtype that reuses or specializes behavior from a base type. A subtype should be substitutable wherever the base contract is expected; overriding a method with stronger assumptions or weaker guarantees can break callers.

class Shape:
    def area(self):
        raise NotImplementedError

class Rectangle(Shape):
    def __init__(self, width, height):
        self.width = width
        self.height = height

    def area(self):
        return self.width * self.height

Use inheritance for a genuine “is-a” relationship with a compatible contract. Do not use it solely to share a few lines of code; composition may be clearer and less coupled.

🏋️ Practice Questions

  1. Why must an override honor the base type's contract?
  2. Give an example where sharing code alone is not a strong reason to inherit.

Module 6 — Polymorphism & Dynamic Dispatch

Shared contract · Multiple implementations

▼

Polymorphism

Polymorphism lets code call the same operation on different implementations through a shared interface. Dynamic dispatch selects an implementation based on the object's runtime type in languages that support it.

def total_area(shapes):
    return sum(shape.area() for shape in shapes)

The caller needs to know the area() contract, not whether each shape is a rectangle, circle, or another valid implementation. This reduces branching in client code when the abstraction is stable.

🏋️ Practice Questions

  1. How does polymorphism reduce type-specific conditionals in total_area?
  2. What is dynamic dispatch?

Module 7 — Composition, Aggregation & Delegation

Has-a · Ownership · Collaboration

▼

Composition

Composition builds an object from collaborators: a service has a repository, or an order has line items. The containing object can delegate work rather than inherit implementation. Clarify who owns each collaborator and how long it lives.

class OrderService:
    def __init__(self, repository, payment_gateway):
        self.repository = repository
        self.payment_gateway = payment_gateway

    def place(self, order):
        self.payment_gateway.charge(order.total)
        self.repository.save(order)

This design makes dependencies visible and replaceable, but it still needs a policy for failures between charging and saving. Composition does not automatically make a workflow transactional.

🏋️ Practice Questions

  1. Identify the collaborators in OrderService.
  2. What failure could occur between charging and saving, and what design might address it?

Module 8 — Interfaces, Protocols & Dependency Inversion

Small contracts · Substitutability

▼

Interfaces

An interface declares operations a caller may rely on; an implementation supplies their behavior. Interfaces can enable substitution, testing, and independent development, but abstractions should remain small and cohesive.

Design choiceBenefitRisk
Concrete dependencyDirect and simpleHarder to substitute when change is needed
Small interfaceDecouples client from implementationExtra abstraction to maintain
Large “god” interfaceOne place to find methodsClients depend on operations they do not use

Dependency Inversion

High-level policy should depend on stable abstractions rather than directly constructing low-level details everywhere. Dependency injection supplies collaborators from outside, commonly through constructor parameters.

🏋️ Practice Questions

  1. Why is constructor injection useful for a service's dependencies?
  2. What is one cost of creating an interface for every class without a client need?

Module 9 — Instance, Class & Static Members

Scope · Shared state · Method binding

▼

Instance and Class State

Instance fields belong to an object. Class-level fields are shared by instances in languages that support them; mutable shared state can create surprising coupling. Keep values on the narrowest scope that matches their lifetime and meaning.

class Session:
    active_count = 0

    def __init__(self):
        self.user_id = None
        Session.active_count += 1

Static Methods and Utility Behavior

Static methods do not operate on a particular instance in languages that provide them. Use them when behavior conceptually belongs near a type but needs no instance or class state; otherwise a module-level function may be simpler.

🏋️ Practice Questions

  1. Which is shared across Session instances: active_count or user_id?
  2. When might a standalone function be clearer than a static method?

Module 10 — Constructors, Factories & Lifecycle

Valid objects · Named creation · Cleanup

▼

Constructors and Validity

Construction should establish an object in a valid state. If initialization has multiple modes or complex validation, named factory methods can make the intent explicit and prevent partially initialized objects.

ApproachExample intent
ConstructorCreate a valid object from required values
Factory methodfrom_config(...) communicates an alternate creation path
BuilderAssemble an object with many optional settings in a readable sequence
Lifecycle methodExplicitly acquire or release an external resource when required

Resource Ownership

Objects that own files, locks, sockets, or transactions need clear cleanup behavior. Prefer language-supported context managers, deterministic destructors, or resource wrappers; do not rely on garbage collection timing for important external effects.

Module 11 — Equality, Immutability & Value Objects

Identity · Hashing · Safe sharing

▼

Entity or Value?

An entity is tracked by identity over time; a value object is defined by its attributes and is often immutable. Immutable values are easier to share and reason about because they cannot change unexpectedly after creation.

Equality and Hashing

If objects are used as dictionary keys or set members, equality and hash behavior must be compatible and stable while stored. Equal values must have equal hashes. Mutable fields that participate in hashing can corrupt lookup behavior after mutation.

🏋️ Practice Questions

  1. Is a user account more naturally an entity or a value object? Why?
  2. What must be true about the hashes of equal objects?

Module 12 — SOLID Design Principles

Responsibility · Extension · Substitution · Interfaces · Dependencies

▼

The Five Principles

PrinciplePractical interpretation
Single ResponsibilityGive a module one cohesive reason to change
Open/ClosedAdd behavior through extension without repeatedly rewriting stable code
Liskov SubstitutionSubtypes preserve the promises clients rely on
Interface SegregationPrefer small client-focused interfaces over a forced large one
Dependency InversionHigh-level policy depends on stable abstractions

Apply Principles with Judgment

SOLID is a set of design heuristics, not a checklist requiring more classes. Use it to identify high coupling or change friction; an abstraction is helpful only when it clarifies an actual boundary.

Module 13 — Common Object-Oriented Patterns

▼

Patterns as Named Trade-offs

PatternProblem it can address
StrategySelect interchangeable behavior behind one contract
FactoryCentralize or name a complex object-creation choice
ObserverNotify subscribers when an event or subject changes

Module 14 — Testing Object-Oriented Designs

Unit tests · Fakes · Contracts

▼

Test Behavior Through Public Contracts

Test observable behavior rather than private implementation details. Use a fake or mock collaborator when a boundary such as email, payment, or storage must be controlled; include integration tests for important real collaborations.

class MemoryRepository:
    def __init__(self):
        self.saved = []

    def save(self, item):
        self.saved.append(item)

Avoid Over-Mocking

Mocking every internal call can make tests pass while behavior is broken and can lock tests to implementation details. Keep objects cohesive, dependencies explicit, and tests focused on meaningful guarantees.

🏋️ Practice Questions

  1. How can constructor injection make a service easier to test?
  2. Name one risk of mocking every method interaction in a unit test.

Module 15 — Refactoring Toward Clear Objects

Code smells · Extract class · Replace conditionals

▼

Signs to Investigate

Repeated conditional logic by type, classes with unrelated responsibilities, long parameter lists, and objects that expose mutable internals can indicate design friction. A smell is a prompt to investigate, not proof that a pattern must be applied.

Refactor Safely

Make a behavior-preserving change in small steps: add or strengthen tests, extract one responsibility, move behavior to the object that owns the relevant state, then rerun the suite. Separate architectural refactors from unrelated feature changes.

🏋️ Practice Questions

  1. What code smell might be suggested by a class with many unrelated reasons to change?
  2. Why is changing one responsibility at a time safer than a broad rewrite?

Module 16 — Model a Reservation System

Entities · Invariants · Collaborators · Failure cases

▼

Start with the Domain and Invariants

Identify the reservation, resource, customer, and time interval. Define what prevents overlapping reservations, what “cancelled” means, how time zones are represented, and which operation owns conflict detection.

Separate Responsibilities

An application service can coordinate authorization, availability, persistence, and notifications. A repository hides persistence details; a notification adapter hides provider details. Keep the overlap invariant enforced atomically at the persistence boundary so concurrent requests cannot both reserve the same interval.

OOP Interview Questions & Answers

Encapsulation · Inheritance · Polymorphism · Design principles

▼

Q: What is the difference between a class and an object?

A class defines a type's structure or behavior; an object is a particular instance with its own identity and state. The class describes what instances can do, while each object represents a concrete runtime entity.

Q: What is encapsulation?

Encapsulation groups state and behavior behind a deliberate boundary. It lets an object protect invariants and change its implementation without requiring callers to manipulate its internals.

Q: What is abstraction?

Abstraction exposes useful operations and guarantees while hiding implementation detail. A client should depend on what a component promises, not how it fulfills that promise.

Q: What is inheritance?

Inheritance defines a subtype from a base type so it can reuse or specialize behavior. Use it for a genuine substitutable “is-a” relationship, not merely to share a few lines of code.

Q: What is polymorphism?

Polymorphism lets different implementations be used through a shared interface. A caller invokes the contract while the runtime or language dispatch rules select the concrete behavior.

Q: What is the difference between overloading and overriding?

Overloading uses the same operation name with different parameter signatures, resolved according to the language's overload rules. Overriding provides a subtype implementation of an inherited virtual or otherwise overridable operation.

Q: What is composition, and when is it preferred to inheritance?

Composition builds an object from collaborating objects and delegates work to them. It is preferred when the relationship is “has-a” or when behavior should be replaceable without coupling a subtype to a base implementation.

Q: What is the Liskov Substitution Principle?

Code using a base contract should continue to behave correctly when given a valid subtype. A subtype should not strengthen required preconditions or weaken promised postconditions in ways that surprise clients.

Q: What is the Single Responsibility Principle?

A module should have one cohesive responsibility or one primary reason to change. It does not mean every method needs its own class; boundaries should reflect meaningful cohesion.

Q: What does “program to an interface” mean?

Clients depend on a stable contract rather than a concrete implementation. This allows alternate implementations, tests, or infrastructure choices without rewriting high-level policy.

Q: What is dependency injection?

Dependency injection supplies an object's collaborators from outside instead of constructing them internally. Constructor injection makes dependencies explicit and can simplify testing and configuration.

Q: What is the difference between an entity and a value object?

An entity is tracked by identity over time, while a value object is defined by its values and is often immutable. The choice affects equality, lifecycle, and how updates are modeled.

Q: Why are immutable objects useful?

Their state cannot change after construction, reducing accidental shared-state changes and simplifying reasoning. They are especially useful for values, though immutability can require copying or replacement when updates are needed.

Q: What is a constructor's responsibility?

A constructor establishes a valid initial state and required invariants. Complex alternate creation paths may be clearer as named factories than as many ambiguous optional parameters.

Q: What is the Open/Closed Principle?

Software entities should support needed extension without requiring repeated changes to stable code. The goal is not to forbid edits, but to place variation behind suitable contracts when change is expected.

Q: What is the Interface Segregation Principle?

Clients should not be forced to depend on operations they do not use. Prefer cohesive, client-focused interfaces over a large general interface with irrelevant methods.

Q: What does the Strategy pattern solve?

It encapsulates interchangeable algorithms behind a common interface so a client can select behavior without embedding every variant in a large conditional.

Q: What is the difference between association, aggregation, and composition?

Association is a general relationship between objects. Aggregation often describes a weak whole-part relationship where parts can outlive the whole; composition describes stronger ownership and lifecycle coupling. Precise semantics vary by modeling convention and language.

Q: How do you test a class with external dependencies?

Test its public behavior and inject controlled collaborators such as fakes for external services. Add integration tests where real persistence, networking, or framework behavior is important; avoid coupling every test to private method calls.

Q: How would you refactor a class with too many responsibilities?

Identify the cohesive reasons it changes, add behavior-focused tests, and extract one responsibility behind a clear interface at a time. Preserve behavior and avoid introducing abstractions without a concrete client need.
