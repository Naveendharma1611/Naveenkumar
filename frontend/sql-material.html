🗄️ What is a Database?

A database is an organised collection of data that can be searched, updated and managed easily. A DBMS (Database Management System) is the software that stores the data and answers your requests — MySQL, PostgreSQL, SQL Server, Oracle and SQLite are all DBMSs.

A relational database (RDBMS) stores data in tables that are linked to each other through keys.

🔤 What is SQL?

SQL (Structured Query Language, said "S-Q-L" or "sequel") is the standard language for relational databases. It is declarative: you describe *what* data you want and the database works out *how* to get it.

SQL was created at IBM in the 1970s and standardised by ANSI/ISO in 1986. Every major database speaks SQL, with small differences called dialects.

    birth_date  DATE,

ALTER TABLE students RENAME TO learners;                -- rename the table

--   MySQL:       ALTER TABLE learners MODIFY name VARCHAR(150);

🗑️ DELETE vs TRUNCATE vs DROP

DELETE FROM learners WHERE home_city = 'Madurai';   -- removes chosen rows
TRUNCATE TABLE learners;                            -- removes ALL rows, keeps the table
DROP TABLE learners;                                -- removes the table itself
DROP TABLE IF EXISTS learners;                      -- no error if it doesn't exist

Module 4 — Constraints & Keys

PRIMARY KEY · FOREIGN KEY · UNIQUE · NOT NULL · CHECK · DEFAULT · Composite keys

▼

🔐 Why Constraints?

Constraints are rules the database enforces so bad data can never get in: no duplicate IDs, no missing names, no orders for customers who don't exist.

ConstraintRule
NOT NULLThe column must have a value
UNIQUENo two rows may have the same value
PRIMARY KEYNOT NULL + UNIQUE; identifies each row (one per table)
FOREIGN KEYThe value must exist in the referenced table
CHECKThe value must satisfy a condition
DEFAULTThe value used when none is given

🔗 Primary and Foreign Keys

CREATE TABLE authors (
    author_id  INT PRIMARY KEY,
    name       VARCHAR(100) NOT NULL UNIQUE
);

CREATE TABLE books (
    book_id    INT PRIMARY KEY,
    title      VARCHAR(200) NOT NULL,
    price      DECIMAL(8, 2) CHECK (price >= 0),
    status     VARCHAR(20) DEFAULT 'available',
    author_id  INT,
    FOREIGN KEY (author_id) REFERENCES authors(author_id)
        ON DELETE SET NULL
        ON UPDATE CASCADE
);

books.author_id now points at authors.author_id. Inserting a book with author_id = 99 fails when author 99 doesn't exist — the database protects the relationship.

ON DELETE optionWhen the parent row is deleted…
NO ACTION / RESTRICT (default)The delete is refused while child rows exist
CASCADEThe child rows are deleted too
SET NULLThe child's foreign key becomes NULL
SET DEFAULTThe child's foreign key gets its default value

🧱 Composite Keys and Named Constraints

CREATE TABLE enrollments (
    student_id  INT,
    course_id   INT,
    enrolled_on DATE,
    PRIMARY KEY (student_id, course_id),     -- the PAIR must be unique
    CONSTRAINT fk_enroll_student FOREIGN KEY (student_id) REFERENCES students(student_id),
    CONSTRAINT fk_enroll_course  FOREIGN KEY (course_id)  REFERENCES courses(course_id)
);

ALTER TABLE books ADD CONSTRAINT uq_book_title UNIQUE (title);   -- add one later
A natural key comes from real data (email, PAN number). A surrogate key is an artificial ID. Most tables use a surrogate primary key plus UNIQUE constraints on the natural keys.
SQLite checks foreign keys only after PRAGMA foreign_keys = ON;.

🎤 One-Line Interview AnswerConstraints enforce data integrity: PRIMARY KEY uniquely identifies rows, FOREIGN KEY keeps references between tables valid, and UNIQUE, NOT NULL, CHECK and DEFAULT protect individual columns.

⚡ What is an Index?

An index is like the index at the back of a book: instead of reading every page (a full table scan), the database jumps straight to the matching rows. Most indexes are B-trees, kept sorted so lookups take about log(n) steps.

Indexes make fasterIndexes make slower / cost
WHERE, JOIN, ORDER BY, GROUP BY on indexed columnsINSERT, UPDATE, DELETE (the index must be updated too)

🛠️ Creating Indexes

CREATE INDEX idx_employees_dept ON employees (dept_id);
CREATE UNIQUE INDEX idx_employees_email ON employees (email);
CREATE INDEX idx_orders_customer_date ON orders (customer_id, order_date);   -- composite

DROP INDEX idx_employees_dept;                 -- PostgreSQL, SQLite
-- MySQL: DROP INDEX idx_employees_dept ON employees;
Primary keys and UNIQUE constraints get an index automatically. Foreign keys usually need one added by you (MySQL adds it for you).

🧭 The Leftmost-Prefix Rule

The composite index on (customer_id, order_date) is sorted by customer first, then date.

WHERE customer_id = 1 AND order_date >= '2024-02-01'Yes, fully
WHERE order_date >= '2024-02-01'No — the first column is missing

🔒 All or Nothing

A transaction groups several statements so they either all succeed or all fail. The classic example is a bank transfer: the money must leave one account and arrive in the other — never just one of the two.

CREATE TABLE accounts (
    id       INT PRIMARY KEY,
    holder   VARCHAR(50),
    balance  DECIMAL(10, 2) CHECK (balance >= 0)
);
INSERT INTO accounts VALUES (1, 'Arun', 5000), (2, 'Priya', 3000);

BEGIN;                                                        -- MySQL: START TRANSACTION;
UPDATE accounts SET balance = balance - 1000 WHERE id = 1;
UPDATE accounts SET balance = balance + 1000 WHERE id = 2;
COMMIT;                                                       -- save both changes together

SELECT id, holder, balance FROM accounts ORDER BY id;
Result

↩️ ROLLBACK and SAVEPOINT

BEGIN;
UPDATE accounts SET balance = balance - 500 WHERE id = 1;
SAVEPOINT after_debit;
UPDATE accounts SET balance = balance + 500 WHERE id = 99;   -- oops: wrong account
ROLLBACK TO SAVEPOINT after_debit;                          -- undo only the last step
UPDATE accounts SET balance = balance + 500 WHERE id = 2;
COMMIT;

-- ROLLBACK;  would undo everything since BEGIN
Most databases run each statement in its own transaction (autocommit) unless you start one with BEGIN.

🧪 ACID Properties

PropertyMeaningBank example
AtomicityAll statements succeed, or none doNo money disappears halfway through a transfer
ConsistencyData moves from one valid state to anotherThe CHECK stops a balance going negative
IsolationTransactions running at the same time don't interfereTwo transfers don't overwrite each other
DurabilityCommitted data survives crashesThe transfer is still there after a power cut

🚦 Isolation Levels

  • Dirty read: reading another transaction's changes before they are committed.
  • Non-repeatable read: reading the same row twice and getting different values.
  • Phantom read: running the same query twice and getting new rows.
Keep transactions short. Long transactions hold locks, block other users and can cause deadlocks (two transactions waiting for each other).

📐 Why Normalise?

Storing everything in one big table repeats data and causes anomalies:

  • Update anomaly: Kumar's email is stored twice — change one and forget the other.
  • Insert anomaly: you can't add a new course until a student joins it.
  • Delete anomaly: delete Ravi's row and you might lose the only record of a course.

🪜 Normal Forms

🧰 Stored Procedures

A stored procedure is a named block of SQL saved in the database that you run with CALL. It can take parameters and contain logic.

-- MySQL
DELIMITER //
CREATE PROCEDURE give_raise(IN p_dept INT, IN p_percent DECIMAL(5, 2))
BEGIN
    UPDATE employees
    SET salary = salary * (1 + p_percent / 100)
    WHERE dept_id = p_dept;
END //
DELIMITER ;

CALL give_raise(2, 10);   -- 10% raise for Sales
DELIMITER // tells the MySQL client that ; inside the procedure doesn't end the whole statement.

A function returns a value and can be used inside a query.

-- PostgreSQL
CREATE OR REPLACE FUNCTION dept_headcount(p_dept INT)
RETURNS INT
LANGUAGE sql

    SELECT COUNT(*)::INT FROM employees WHERE dept_id = p_dept;

⚡ Triggers

A trigger runs automatically when rows are inserted, updated or deleted — perfect for audit logs.

CREATE TABLE salary_audit (
    emp_id      INT,
    old_salary  DECIMAL(10, 2),
    new_salary  DECIMAL(10, 2),
    changed_at  TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- MySQL
DELIMITER //
CREATE TRIGGER trg_salary_audit
AFTER UPDATE ON employees
FOR EACH ROW
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit (emp_id, old_salary, new_salary)
        VALUES (OLD.emp_id, OLD.salary, NEW.salary);
    END IF;
END //
DELIMITER ;
-- PostgreSQL: a trigger function + the trigger
CREATE OR REPLACE FUNCTION log_salary_change() RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
    IF NEW.salary <> OLD.salary THEN
        INSERT INTO salary_audit (emp_id, old_salary, new_salary)
        VALUES (OLD.emp_id, OLD.salary, NEW.salary);
    END IF;
    RETURN NEW;
END;
$$;

Module 22 — Users, Permissions & SQL Injection

CREATE USER · GRANT · REVOKE · Roles · SQL injection · Backups

👤 Users and Permissions (DCL)

-- MySQL
CREATE USER 'report_user'@'localhost' IDENTIFIED BY 'Str0ng!Passw0rd';
GRANT SELECT ON company.* TO 'report_user'@'localhost';           -- read-only
GRANT SELECT, INSERT, UPDATE ON company.orders TO 'report_user'@'localhost';
REVOKE INSERT, UPDATE ON company.orders FROM 'report_user'@'localhost';

-- PostgreSQL
CREATE USER report_user WITH PASSWORD 'Str0ng!Passw0rd';
GRANT SELECT ON ALL TABLES IN SCHEMA public TO report_user;

👥 Roles

A role is a named bundle of permissions. Grant permissions to the role, then give the role to people.

CREATE ROLE analyst;
GRANT SELECT ON employees, departments TO analyst;
GRANT analyst TO report_user;
Follow the principle of least privilege: every user and application gets only the permissions it actually needs. Web apps should never connect as the database admin.

💉 SQL Injection

SQL injection happens when user input is glued into SQL text. An attacker can type SQL instead of data.

name = input("Name: ")        # the attacker types:   ' OR '1'='1

# ❌ Vulnerable: the input becomes part of the SQL
cur.execute(f"SELECT * FROM users WHERE name = '{name}'")
# runs: SELECT * FROM users WHERE name = '' OR '1'='1'   → returns EVERY user

# ✅ Safe: parameters are sent separately and never run as SQL
cur.execute("SELECT * FROM users WHERE name = %s", (name,))   # MySQL / PostgreSQL drivers
cur.execute("SELECT * FROM users WHERE name = ?", (name,))    # sqlite3
Always use parameterised queries (or an ORM). Never build SQL by joining strings with user input.

💾 Other Essentials

  • Store password hashes (bcrypt, Argon2), never plain passwords
  • Use encrypted connections (TLS) and keep the database off the public internet
  • Take regular backups and test restoring them: mysqldump company > backup.sql, pg_dump company > backup.sql
