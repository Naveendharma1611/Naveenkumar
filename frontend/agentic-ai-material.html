Module 1 — What Is an AI Agent?

Goal-directed · Multi-step · Tool-using

▼

🧭 An agent pursues a goal, a chatbot answers a message

A chatbot is turn-based: it reads one message, produces one response, and waits. An AI agent is given a goal and runs a loop — it decides what to do next, takes an action (often calling a tool), observes the result, and decides again, continuing autonomously until the goal is met, it hits a limit, or it gives up and asks for help. The LLM is still the reasoning core in both cases; what changes is that the agent wraps the LLM in a control loop that lets it act on the world and react to what happens, instead of just emitting text back to a human.

This distinction matters practically: "add an agent to our chatbot" usually means adding a loop, a set of callable tools, and a stopping condition — not a different model. Many products marketed as "AI agents" are really a single LLM call with a slightly longer prompt; a genuine agent exhibits multi-step, conditional behavior where the number and sequence of steps is not fixed in advance.

🔗 Agent vs single LLM call vs RAG

Three terms get blurred constantly. A single LLM call takes an input, produces an output, and stops — no tools, no loop. RAG (retrieval-augmented generation) adds one deterministic step before the call: retrieve relevant documents, stuff them into the prompt, generate an answer — still a fixed, one-shot pipeline. An agent is open-ended: it decides, at run time, which tools to call, how many times, and in what order, based on what it has already observed. RAG can be — and often is — one tool available to an agent, rather than a separate category; the agent decides whether retrieval is even needed for a given step.

PatternStepsDecides its own next step?Example
Single LLM call1NoSummarize this email
RAG pipelineFixed: retrieve, then generateNo, the sequence is hard-codedAnswer a question using a knowledge base
AgentVariable, run-time decidedYesResearch a topic, write code, fix the failing test, report back

🧩 The ingredients every agent has

Strip away the branding and every agent architecture has the same four parts: (1) an LLM core that reasons about the current state and decides the next action; (2) a set of tools the LLM can invoke — functions with defined inputs and outputs; (3) memory — the running context of what has happened so far, sometimes backed by persistent storage; (4) a control loop that executes the chosen action, feeds the result back, and decides whether to continue or stop. Everything covered in this material is a variation on how these four pieces are built and connected.

🏋️ Practice Questions

  1. Give an example of a task better solved by a single LLM call than by an agent, and explain why adding a loop would be wasteful.
  2. Explain why a RAG pipeline is not automatically an "agent," and describe one change that would make it one.
🎤 One-Line Interview AnswerAn AI agent differs from a chatbot or a plain RAG pipeline by running a loop where it decides, at run time, which tools to call and in what order toward a goal, rather than following a fixed one-shot sequence.

Module 2 — The Agent Loop

Perceive · Reason · Act · Observe

▼

🔁 Perceive → reason → act → observe

The canonical agent loop has four phases repeated until the goal is met: perceive (gather the current state — the user's goal, conversation history, any tool results so far), reason (the LLM decides what to do next: answer directly, or call a tool), act (execute the chosen action — run the tool, call the API), observe (append the result to the context and loop back to perceive). Each iteration is sometimes called a "step" or a "turn" of the agent, and most production agents cap the number of steps to bound cost and prevent infinite loops.

🪜 A worked trace through one step

Imagine an agent with the goal "find this week's top story on a news site and summarize it." Step 1 — perceive: the agent has the goal and no prior results. Reason: the LLM decides it needs to browse the site first, so it requests a fetch_page tool call with the site's URL. Act: the control loop executes fetch_page(url=...) and gets back raw page content. Observe: that content is appended to the agent's context. Step 2 — perceive: the agent now has the goal plus the page content. Reason: the LLM decides it has enough information and should extract and summarize the top story directly, with no further tool call. Act: it generates the summary as its final answer. Observe: the loop's stopping condition — a final answer with no tool call requested — is met, and the loop ends.

PhaseWhat happensWho or what performs it
PerceiveAssemble current state: goal, history, last tool resultControl loop
ReasonDecide next action: answer, or call which tool with what argumentsLLM
ActExecute the chosen tool callControl loop / tool runtime
ObserveAppend the result to context, check stop conditionControl loop
Log every (reason, act, observe) triple per step during development. When an agent misbehaves, this trace is almost always more useful for debugging than the final output alone — the failure usually happened several steps earlier than where it became visible.

🏋️ Practice Questions

  1. Walk through the perceive-reason-act-observe cycle for an agent that needs to book a meeting room, checking two calendars before confirming.
  2. What should the control loop do if the LLM requests a tool that does not exist in the available tool list?
🎤 One-Line Interview AnswerThe agent loop is perceive, reason, act, observe, repeated: the loop assembles the current state, the LLM decides the next action, the control layer executes it, and the result feeds back into context until a stopping condition — like a final answer with no further tool call — is reached.

Module 3 — Tool / Function Calling Mechanics

Schemas · Requests · Results

▼

🛠️ How the LLM is given tools

The LLM doesn't execute code — it only produces text or structured output. Function/tool calling works by giving the model a list of tool definitions: each tool's name, a natural-language description of what it does, and a schema (usually JSON Schema) describing its expected arguments. The model is trained to recognize, from the conversation and these definitions, when calling a tool would help, and to emit a structured request — typically a JSON object naming the tool and its arguments — instead of a plain-text reply. The host application, not the model, is responsible for actually running the tool and returning its result.

📨 The full round trip

The sequence is always: (1) the application sends the model the conversation plus the tool definitions; (2) the model replies with either a normal text answer, or a structured "call this tool with these arguments" request; (3) the application parses that request, validates the arguments against the schema, and executes the real function (a search, a database query, a calculation); (4) the application appends the tool's result to the conversation as a new message, tagged as coming from that tool; (5) the model is called again with this extended conversation and decides what to do next — answer, or call another tool. Nothing here requires a special "agent mode" — it is the same conversational API, just with an extra message type for tool calls and tool results.

Conversation so far:
  user: "What's the weather in Chennai and should I bring an umbrella?"

Tools offered to the model:
  get_weather(city: string) -> { condition, temp_c, rain_chance }

Round 1 - model reply (structured, not plain text):
  tool_call: get_weather(city="Chennai")

Application executes get_weather("Chennai"):
  -> { condition: "cloudy", temp_c: 29, rain_chance: 0.6 }

Round 2 - model is called again with the tool result appended:
  tool_result: get_weather -> { condition: "cloudy", temp_c: 29, rain_chance: 0.6 }

Round 2 - model reply (plain text, no further tool call):
  "It's cloudy in Chennai, 29C with a 60% chance of rain -
   worth bringing an umbrella."

📝 What makes a good tool definition

Tool descriptions are prompts, not documentation for humans — vague descriptions produce wrong or missed calls. A good tool definition names exactly what the tool does, states its argument types and constraints precisely (is date a string in YYYY-MM-DD, or a Unix timestamp?), says what it returns, and ideally gives an example. Narrow, single-purpose tools (get_weather, search_flights) are far more reliable than one broad tool with a free-text "instructions" argument, because the model has less room to misuse a tightly scoped interface.

The model can request a tool call with plausible-looking but invalid arguments — a made-up city name, a field the schema doesn't define, a string where a number was required. Always validate tool-call arguments before executing anything, exactly as you would validate any other untrusted input.

🎤 One-Line Interview AnswerFunction calling works by giving the LLM structured tool definitions — name, description, argument schema; the model emits a structured request to call one, the application executes the real function and returns the result as a new message, and the model is invoked again with that result in context to decide its next step.

Module 4 — Giving an Agent Real Tools

Search · Code exec · File access · APIs

▼

🔎 Common categories of tools

Most production agents draw from a small set of tool categories: search / retrieval (web search, a vector database, an internal knowledge base) to pull in information the model doesn't have; code execution (a sandboxed interpreter) for calculation, data manipulation, or testing generated code; file / document access (read, write, list) for working with a user's files; and internal API calls (CRM lookups, ticket creation, payment actions) that let the agent actually change something in the world, not just read it. The riskiest tools are the ones with side effects — anything that sends an email, spends money, deletes data or modifies a record — and they deserve the most scrutiny before being handed to an autonomous loop.

🏗️ Designing the tool, not just wrapping an API

A tool is not simply "expose this existing API endpoint to the model." Good tool design shapes the interface for how an LLM will use it: collapse multi-step API flows into one tool call where possible, return concise structured results instead of a raw dump the model has to re-parse, use clear error messages the model can act on ("no flights found for that date" rather than an HTTP 404), and bound what a tool can do — a run_sql tool that only allows SELECT statements, never DROP or DELETE, is a different and much safer tool than raw database access.

Tool categoryExamplePrimary risk if misused
Search / retrievalWeb search, vector DB lookupOutdated or irrelevant context pollutes reasoning
Code executionSandboxed Python interpreterResource exhaustion, unsafe code, data exfiltration
File accessRead/write to a workspaceOverwriting or leaking sensitive files
Internal API / actionSend email, create a ticket, charge a cardReal-world side effects that can't be undone
Read-only tools (search, lookups, calculations) are low-risk to let an agent call freely. Write/action tools (sending, charging, deleting) are where the guardrails covered in Module 11 — permission boundaries, approval steps, sandboxing — actually matter.

🏋️ Practice Questions

  1. Take a raw "update customer record" API with 12 optional fields and redesign it as a tighter tool for an agent to call safely.
  2. Explain why collapsing a 3-step API flow into a single tool call usually improves agent reliability.
🎤 One-Line Interview AnswerGood agent tools aren't just wrapped API endpoints — they're purpose-built interfaces with narrow scope, clear structured results and actionable error messages, with read-only tools treated very differently from tools that have real side effects like sending money or deleting data.

Module 5 — Reasoning Patterns: ReAct & Chain-of-Thought for Agents

Interleaved reasoning · Reliability

▼

🧠 Why explicit reasoning improves tool use

Asking a model to jump straight from a goal to a tool call often produces a plausible-sounding but wrong action, especially for multi-step tasks. The ReAct pattern (Reason + Act) has the model interleave short reasoning steps with actions: before each tool call, the model writes a brief "thought" explaining what it's trying to find out and why this tool is the right next step, then issues the call, observes the result, and reasons again before the next action. This externalizes the model's intermediate reasoning so it can be inspected, logged and conditioned on, which measurably reduces wrong or redundant tool calls compared to asking for an action with no stated reasoning.

🔁 A ReAct trace

Goal: "Is it cheaper to fly or take the train from city A to city B next Friday?" Thought: I need flight prices first. Action: search_flights(from=A, to=B, date=next_friday). Observation: cheapest flight $120. Thought: Now I need train prices for the same route and date to compare. Action: search_trains(from=A, to=B, date=next_friday). Observation: cheapest train $65. Thought: I have both prices now, I can answer directly without another tool call. Final answer: "The train is cheaper at $65 vs $120 for the flight." Each thought is short and purpose-built — it states what's missing and what action will supply it — rather than being a long free-form essay.

⚖️ Reasoning effort vs latency and cost

More reasoning per step is not free: every thought is extra tokens, extra latency, and extra cost, multiplied across every step of a multi-step run. Teams tune how much explicit reasoning to ask for based on task difficulty — a well-scoped single-tool lookup rarely needs a written thought at all, while a multi-step research or debugging task benefits noticeably from it. Chain-of-thought-style reasoning before acting is a reliability lever to spend deliberately, not a default to maximize everywhere.

🏋️ Practice Questions

  1. Rewrite the flight-vs-train trace above as a plain action-only sequence with no thoughts, and explain what information is lost for someone debugging a wrong answer.
  2. Describe a task where you'd skip explicit reasoning steps entirely, and why that's the right trade-off.
🎤 One-Line Interview AnswerReAct interleaves short reasoning steps with tool calls — the model states what it needs before each action — which makes intermediate decisions inspectable and reduces wrong or redundant tool calls, at the cost of extra tokens and latency that should be spent in proportion to task difficulty.

Module 6 — Planning & Task Decomposition

Sub-tasks · Re-planning

▼

🗺️ Breaking a goal into sub-tasks

Complex goals rarely map to a single tool call. Planning is the step where the agent, explicitly or implicitly, breaks a goal into an ordered sequence of smaller sub-tasks before or while executing them — e.g. "migrate this script to the new API" decomposes into: read the current script, identify calls to the old API, look up the new API's equivalents, rewrite each call, run the tests, fix failures. Some agents generate this plan up front as a visible list; others plan implicitly, one step at a time, deciding the next sub-task only after seeing the previous result. Up-front plans are easier to review and show a user before execution; step-by-step planning adapts better when early steps reveal information that changes the right next move.

🔄 Re-planning when a step fails

A plan made before execution starts is a guess, and real steps fail: a search returns nothing useful, a file doesn't exist, a test still fails after a fix. A robust agent treats its plan as revisable — when a step's outcome contradicts what the plan assumed, it updates the plan rather than blindly continuing down a now-invalid sequence. This typically means feeding the failure back into the reasoning step and explicitly asking "given this result, what should happen next" rather than mechanically executing a frozen list of steps regardless of what's actually occurring.

Planning styleHow it worksStrengthWeakness
Plan-then-executeGenerate the full step list up front, then run itReviewable before any action is takenBrittle if an early step's result invalidates later steps
InterleavedDecide only the next step, after seeing the last resultAdapts naturally to surprisesHarder to show the user "the plan" in advance
HierarchicalHigh-level plan broken into sub-plans per sub-goalScales to large, multi-part goalsMore moving parts, more places to go wrong
For anything with real-world side effects, surface the plan to a human before execution even if the agent plans step-by-step internally — showing "here's what I'm about to do" is cheap and catches wrong plans before they run, not after.

🏋️ Practice Questions

  1. Decompose "onboard a new employee" into a sub-task sequence an agent with access to HR, IT and email tools could execute.
  2. Describe a scenario where plan-then-execute would fail silently in a way that interleaved planning would catch.
🎤 One-Line Interview AnswerPlanning is decomposing a goal into an ordered sequence of sub-tasks, either up front or step-by-step; the harder and more valuable half is re-planning — treating the plan as revisable and updating it when a step's actual result contradicts what was assumed.

Module 7 — Agent Memory

Short-term · Long-term · Vector stores

▼

🗂️ Short-term memory: the context window

The simplest form of agent memory is the running conversation and tool-result history kept directly in the LLM's context window for the current run. It's exact — nothing is summarized or lost — and requires no extra infrastructure, but it's bounded: every tool result, every reasoning step, every observation adds tokens, and a long-running agent will eventually fill the context window, drive up cost and latency, and in the worst case push earlier, still-relevant information out or degrade reasoning quality as the context grows. Short-term memory is naturally scoped to a single run; it doesn't survive between separate sessions unless explicitly saved.

💾 Long-term memory: summarizing and persisting

For anything that must survive beyond one run — a user's preferences, facts learned in a past session, outcomes of previous tasks — agents need long-term memory: information stored outside the context window and retrieved when relevant, rather than carried in full every time. Two common techniques are summarization (periodically compress older parts of the conversation into a shorter summary that replaces the verbose history) and retrieval from a vector database (store facts or past interactions as embeddings, then pull back only the handful relevant to the current step, much like RAG). The two combine well: summarize to control context-window growth within a single long run, and persist to a vector store or database for facts that must be available across runs.

Memory typeLives whereSurvives across runs?Typical technique
Short-termContext windowNoRaw conversation plus tool history
Long-term, sessionSummarized into contextWithin the run onlyPeriodic summarization
Long-term, persistentExternal storeYesVector database, key-value store, SQL table

⚖️ When to summarize vs when to store

Summarize when the information is only useful as context for continuing the current task ("we already tried X and it failed") — a compressed version is enough and keeps token cost down. Store in a retrievable long-term memory when the information is a discrete, reusable fact likely to matter again later, independent of this specific run, such as a user's stated preference or a decision that was made and why. A common mistake is dumping everything into a vector store "just in case" — retrieval quality degrades as the store fills with low-value entries, so long-term memory benefits from being curated, not exhaustive.

🏋️ Practice Questions

  1. For a coding agent working across a multi-hour session, decide what belongs in short-term context vs what should be summarized.
  2. Give an example of a fact worth persisting in long-term memory for a customer-support agent, and one that is not worth persisting.
🎤 One-Line Interview AnswerAgent memory splits into short-term context-window memory, which is exact but bounded by token limits and doesn't survive between runs, and long-term memory via summarization or a persistent store like a vector database, which trades some fidelity for surviving across sessions and keeping context usage under control.

Module 8 — Single-Agent vs Multi-Agent Systems

Orchestrator · Worker · Complexity

▼

🤝 When one agent is enough

A single agent with a good set of tools and a solid loop handles the large majority of real tasks — most goals, even multi-step ones, don't actually need separate specialized agents coordinating with each other. The default assumption should be a single agent; splitting into multiple agents is a design decision to justify, not a default to reach for because it sounds more sophisticated.

🧩 When multiple agents genuinely help

Multi-agent designs earn their complexity in specific situations: when sub-tasks require genuinely different tool sets or specialized prompting that would otherwise bloat one agent's instructions past the point of reliability (a "research" agent vs a "writing" agent vs a "fact-checking" agent); when sub-tasks can run in parallel and independent agents working concurrently finish faster than one agent working serially; or when isolating context matters — keeping a long, noisy sub-task's history out of the main agent's context window so it doesn't dilute the main reasoning. A common pattern is orchestrator/worker: one orchestrator agent breaks the goal into sub-tasks and dispatches each to a worker agent, sometimes a different, cheaper or more specialized model, then integrates the workers' results back into a final answer.

⚠️ The complexity and failure-surface cost

Every additional agent is another place for things to go wrong: message formats between agents can be misinterpreted, an orchestrator can give a worker an ambiguous sub-task, errors can silently compound as they pass through multiple agents before surfacing, and debugging requires tracing a failure across agent boundaries instead of through one coherent log. Multi-agent systems also roughly multiply cost and latency per additional agent involved in a run. The practical rule: a single, well-designed agent beats a multi-agent system for most tasks; reach for multiple agents only when a single agent demonstrably can't do the job well, not because the task merely sounds complex.

SignalSuggests
One coherent set of tools and instructions handles the taskSingle agent
Sub-tasks need very different, conflicting system prompts or tool setsMultiple specialized agents
Sub-tasks are independent and can run at the same timeMultiple agents in parallel, orchestrated
Task is "complex" but each step still fits one tool/context cleanlyStill probably a single agent, just more steps
Multi-agent systems are often reached for prematurely because they sound more impressive, not because they're needed. The added coordination overhead and failure surface is real cost — treat it as a trade-off to justify with a concrete reason, not a default architecture.

🏋️ Practice Questions

  1. Describe a task where an orchestrator/worker split clearly beats a single agent, and name the specific reason: parallelism, context isolation, or specialization.
  2. Describe a task someone might split into three agents unnecessarily, and explain how a single agent with more steps would do just as well.
🎤 One-Line Interview AnswerA single, well-scoped agent handles most tasks and should be the default; multi-agent systems earn their added coordination and failure-surface cost only when sub-tasks need genuinely different specialization, real parallelism, or context isolation — not just because a task sounds complex.

Module 9 — Popular Agent Patterns in Practice

Coding agent · Research agent · Support agent

▼

💻 A coding agent

A coding agent's tools typically include reading and writing files, running a shell command, running the test suite, and sometimes searching the codebase or the web. Its loop usually looks like: read the relevant files for context, propose a change, write it, run the tests, and if they fail, reason about the failure and try again — a tight, self-correcting cycle where the test suite acts as an automatic, trustworthy observation rather than relying on the model to judge its own correctness. The biggest reliability win for this pattern is having a fast, deterministic feedback signal — tests, a linter, a type checker — the agent can act on, rather than depending on the model to assess its own output.

🔎 A research agent

A research agent's core tool is search — web, documents, an internal knowledge base — and its loop is closer to iterative investigation: issue a search, read the results, decide what's still missing or contradictory, search again with a refined query, and eventually synthesize findings into an answer with sources. The main failure mode to design against is shallow, single-pass research that stops after the first plausible-looking result — good research agents are explicitly pushed, via prompting or a minimum-step requirement, to cross-check claims across more than one source before finalizing an answer.

🎧 A customer-support agent

A support agent typically has read access to account or order data, a knowledge base, and narrowly-scoped write tools for actions like issuing a refund up to a limit or updating a shipping address. The defining design question here is the boundary between what it can do autonomously and what requires human approval — a support agent that can look up an order and draft a response autonomously but must get explicit approval before issuing a refund over some threshold is a common and sensible split. The tone and scope of its tools matter as much as its reasoning: a support agent needs tightly bounded actions specifically because mistakes here have direct cost and direct customer impact.

PatternCore toolsKey reliability lever
Coding agentFile read/write, shell, test runnerDeterministic feedback (tests, linter) instead of self-judgment
Research agentWeb / document searchForcing multi-source cross-checking, not stopping at first result
Support agentAccount data, knowledge base, scoped write actionsClear autonomous-vs-approval-required action boundary

🏋️ Practice Questions

  1. For a coding agent, explain why "run the tests" is a more reliable stopping signal than asking the model "are you confident this is correct?"
  2. Design the action boundary for a support agent: which 3 actions should it take autonomously, and which 2 should always require human approval?
🎤 One-Line Interview AnswerThe common agent patterns — coding, research, support — differ mainly in their tools and their reliability lever: coding agents lean on deterministic test feedback, research agents on forced multi-source cross-checking, and support agents on a clear boundary between autonomous actions and ones that need human approval.

Module 10 — Building a Simple Agent Loop

Worked Python pseudocode

▼

🐍 The loop, stripped to its essentials

Below is vendor-neutral pseudocode for the simplest possible agent loop: call the LLM, check whether it requested a tool, run the tool if so, feed the result back, and repeat until it answers directly or a step limit is hit. Every production agent framework is a more elaborate version of this same shape — the core mechanics rarely change, even when the surrounding code handles streaming, parallel tool calls, retries, and richer memory.

def run_agent(goal, tools, llm_call, max_steps=10):
    messages = [{"role": "user", "content": goal}]
    tool_defs = [t.schema for t in tools]
    tool_by_name = {t.name: t for t in tools}

    for step in range(max_steps):
        response = llm_call(messages, tools=tool_defs)

        if response.tool_call is None:
            # Model answered directly - we're done.
            return response.text

        call = response.tool_call
        tool = tool_by_name.get(call.name)

        if tool is None:
            result = {"error": f"no such tool: {call.name}"}
        else:
            try:
                result = tool.run(**call.arguments)
            except Exception as e:
                result = {"error": str(e)}

        # Record both the model's requested call and the tool's result,
        # so the next call to the model sees the full exchange.
        messages.append({"role": "assistant", "tool_call": call})
        messages.append({"role": "tool", "name": call.name, "content": result})

    return "Stopped: reached max_steps without a final answer."

🔍 What each part is doing and why it matters

messages is the agent's short-term memory — everything accumulates here, which is exactly why context-window growth, covered in Module 7, is a real constraint on long runs. The max_steps cap exists to bound an agent that gets stuck requesting tool calls indefinitely, Module 12's "infinite loop" failure mode — without it, a buggy or confused agent can run, and cost money, forever. Wrapping tool.run(...) in a try/except and feeding errors back as a normal tool result, rather than crashing, lets the model see the failure and reason about what to do next — retry with different arguments, try a different tool, or give up and report the problem — which is far more robust than letting an exception halt the whole run.

🏋️ Practice Questions

  1. Modify the pseudocode so the loop also stops and returns an explicit "needs human approval" result when a tool is tagged as requiring approval, rather than running it.
  2. Explain what would go wrong if tool errors were allowed to raise and crash the loop instead of being caught and fed back as a result.
🎤 One-Line Interview AnswerA minimal agent loop is just: call the LLM with the available tools, check if it requested a tool call, execute it and feed the result back as a new message, and repeat until the model answers directly or a step limit is hit — nearly every production agent framework is a more elaborate version of this same core loop.

Module 11 — Guardrails & Safety for Autonomous Action

Permissions · Approval · Sandboxing

▼

🔒 Permission boundaries on tools

Not every tool should be callable freely just because the agent decided to call it. Read-only, reversible tools — search, lookups — are low risk to run autonomously. Tools with real side effects, such as spending money, sending communications, deleting data or modifying external records, need an explicit permission boundary: a per-tool policy deciding whether the agent can call it autonomously, call it only within limits (refunds under $50, for example), or must always route through human approval regardless of amount. This boundary should be enforced in code at the tool-execution layer, not left to the model to "decide to be careful" — a model instruction not to do something risky is a prompt, not a control, and prompts can be worked around or simply misjudged under pressure of an in-context scenario.

✋ Requiring approval for risky actions

For actions above the autonomous-permission line, the standard pattern is: the agent proposes the action and its arguments, execution pauses, a human (or a separate, simpler automated check) approves or rejects it, and only on approval does the tool actually run. This is the same idea as Module 14's human-in-the-loop checkpoints, applied specifically as a safety mechanism rather than a UX choice — it exists to put a stop before an irreversible action, not just to keep a human informed after the fact.

🧪 Rate limits and sandboxing

Two further layers catch what approval gates miss. Rate limits cap how many times a given tool, or any tool, can be called within a run or a time window, which bounds runaway cost from a looping agent and limits the blast radius of a single bad decision repeated many times. Sandboxing runs risky tools — especially code execution and file access — in an isolated environment with no access to production systems, secrets, or the wider filesystem/network by default, so that even a successfully "exploited" or badly-reasoned tool call can't reach anything it shouldn't. Sandboxing and permission boundaries are complementary: permissions decide whether an action is allowed to run, sandboxing limits what it can reach if it does.

GuardrailStopsEnforced where
Permission boundaryAutonomous execution of actions above a risk thresholdTool-execution layer, in code
Human approval checkpointAn irreversible or high-stakes action happening without reviewBefore the tool call is executed

A system-prompt instruction like "never delete files without asking" is advice to the model, not an enforced control — it can be overridden by a confusing context, a long conversation that drifts, or simply a wrong model decision. Real safety boundaries are enforced in code at the point the tool actually executes, independent of what the model "intended."

🎤 One-Line Interview AnswerGuardrails for autonomous agents are enforced in code at the tool layer, not through model instructions alone: permission boundaries decide which actions can run autonomously versus needing human approval, rate limits bound runaway cost or repeated mistakes, and sandboxing limits what a risky tool call can actually reach even if it's approved to run.

Module 12 — Common Failure Modes

Loops · Hallucinated calls · Context overflow

▼

🔁 Infinite or repetitive loops

An agent can get stuck calling the same tool repeatedly with slightly different arguments, never recognizing that the approach isn't working — retrying a failing search query with cosmetic rewordings indefinitely, or alternating between two tool calls that undo each other's effect. This happens because the model has no inherent sense of "I've tried this before and it didn't help" unless that history is visible and the model is prompted to notice it. Mitigations: a hard max_steps cap, detecting repeated identical or near-identical tool calls and surfacing that explicitly to the model — "you already tried this exact search and got no results, try a different approach" — and in some designs, escalating to a human after N unsuccessful attempts at the same sub-goal.

🧩 Hallucinated tool calls and arguments

The model can request a tool that doesn't exist, or call a real tool with arguments that look plausible but are fabricated — a made-up file path, an invented order ID, a parameter value it never actually observed anywhere in context. This is the same underlying hallucination behavior seen in plain LLM text generation, just manifesting as a structured call instead of a false sentence, and it's more dangerous here because a hallucinated argument can trigger a real action rather than just displaying a wrong fact. Mitigation is the same discipline as validating any untrusted input: validate tool-call arguments against the schema and, where possible, against ground truth, then return a clear "not found / invalid" tool result rather than letting a bad value propagate.

📈 Context window overflow from long histories

As a run accumulates steps, the full history of reasoning, tool calls and results keeps growing, and a long enough run will eventually exceed the context window or degrade reasoning quality well before hitting the hard limit, since models tend to attend less reliably to information buried in the middle of a very long context. This is the practical reason Module 7's memory strategies — summarizing older steps, dropping tool results that are no longer relevant, persisting facts externally instead of keeping them inline — aren't optional polish for long-running agents; without them, a sufficiently long task simply breaks.

🌊 Cascading errors across steps

Because each step's context includes everything before it, an early mistake — a slightly wrong fact retrieved, a misread tool result, a wrong assumption stated in a reasoning step — doesn't just affect that step; it becomes part of the "ground truth" every subsequent step reasons from, and the agent can build an increasingly confident, increasingly wrong chain of actions on top of it. This is why catching errors early — validating tool results, sanity-checking surprising outputs — is disproportionately valuable compared to catching them late, and why some designs include a periodic self-check step that re-examines the plan against the actual goal rather than trusting accumulated context blindly.

  2. Explain why a hallucinated tool argument is more dangerous in an agent than a hallucinated fact in a plain chatbot answer.
🎤 One-Line Interview AnswerThe most common agent failure modes are getting stuck in repetitive loops with no sense of prior failed attempts, hallucinating tool calls or arguments that trigger real actions on fabricated input, context-window overflow from long accumulated histories, and early mistakes cascading into increasingly confident wrong chains of later steps.

Module 13 — Evaluating Agents

Success rate · Efficiency · Cost

▼

🧪 Why evaluating an agent is harder than evaluating one response

Evaluating a single LLM response is comparatively simple: judge one output against a reference or a rubric. Evaluating an agent run means judging a whole trajectory — a variable-length sequence of decisions, tool calls and intermediate results — where there can be more than one valid path to the same correct final answer, and where a correct final answer can still hide an inefficient, lucky, or risky path to get there. A good evaluation framework looks at both the outcome and the process: did it succeed, and was the way it succeeded acceptable — right number of steps, no unnecessary risky actions, no wasted cost?

📊 The core metrics

Task success rate — did the run actually achieve the goal, checked against a ground-truth outcome where possible rather than just "did it sound right." Step efficiency — how many steps or tool calls it took relative to a reasonable minimum; more steps than necessary usually signals confused or redundant reasoning, not thoroughness. Cost and latency per run — total tokens and wall-clock time across the whole trajectory, since these compound multiplicatively with more steps and matter directly for production viability. Tool-call correctness — of the tool calls made, how many had valid, sensible arguments and were actually necessary for the goal, independent of whether the final answer happened to be right anyway.

MetricMeasuresWhy it's not enough alone
Task success rateDid the run reach the correct outcomeA lucky or wasteful path can still "succeed"
Step efficiencySteps taken vs a reasonable minimumA short run can also be short because it gave up early
Cost / latency per runTokens and time consumedSays nothing about correctness
Tool-call correctnessValid, necessary calls vs invalid/unnecessary onesDoesn't capture whether the final answer was right

🔬 Building an evaluation set

Agent evaluation needs a set of representative tasks with known correct outcomes, or a reliable way to check the outcome programmatically — "did the test suite end up passing," "does the database row have the expected new value" — rather than relying solely on an LLM-as-judge reading the transcript. Tasks should include both straightforward cases and ones designed to probe the specific failure modes from Module 12 — a task where a tool deliberately returns an error, a task with a misleading early search result, a long task that stresses context limits — since those are exactly the situations where agents tend to break in production but a narrow "happy path" eval set would never surface.

🎤 One-Line Interview AnswerEvaluating an agent means judging a whole trajectory, not one response — task success rate alone isn't enough, so a real evaluation also tracks step efficiency, cost and latency per run, and tool-call correctness, using tasks with programmatically checkable outcomes that specifically probe known failure modes.

Module 14 — Human-in-the-Loop Design

Checkpoints · Plans · Audit logs

▼

✅ Approval checkpoints

The most direct human-in-the-loop mechanism is an approval checkpoint: before a specific action executes — typically one that's irreversible, costly, or high-stakes, per Module 11's permission boundaries — the agent pauses and a human explicitly approves or rejects it before anything happens. The design question is where to place these checkpoints: too many, and the agent is barely autonomous and the human becomes a bottleneck who starts rubber-stamping without really checking; too few, and risky actions execute without real oversight. A practical default is to gate checkpoints on consequence, not on task type: low-stakes reversible steps run autonomously regardless of how many there are, while the rare high-stakes step always pauses.

📋 Showing the plan before acting

For multi-step tasks, showing the agent's intended plan to the user before execution begins — "here's what I'm going to do: 1) ... 2) ... 3) ..." — lets a human catch a wrong approach at the cheapest possible point, before any step has run, rather than discovering the problem after several actions have already executed and possibly need to be undone. This is distinct from per-action approval: it's a single, cheap review of the overall approach rather than a checkpoint on every individual step, and it works well even for agents that mostly run autonomously once the plan is approved.

🧾 Audit logs of agent actions

Every tool call an agent makes — what was called, with what arguments, what it returned, and which step of which run it belonged to — should be logged in a durable, queryable audit trail, independent of whether anything went wrong. This serves three purposes: debugging a specific failure after the fact by reconstructing exactly what the agent did and why; accountability, since "the agent decided to do X" needs to be traceable to a specific, inspectable decision rather than being a black box; and compliance, in domains such as finance or healthcare, where an autonomous action needs a record regardless of outcome. An audit log is not a replacement for approval checkpoints on risky actions — it's a record of what happened, not a gate on what's allowed to happen.

MechanismWhen it happensWhat it catches
Plan reviewBefore any step executesA wrong overall approach, caught at minimum cost
Approval checkpointBefore a specific high-stakes actionA risky individual action, before it runs
Audit logAfter every action, continuouslyEnables debugging and accountability after the fact
Treat "what does a human need to see, and when" as a first-class design question for every agent with real-world actions, not an afterthought bolted on after the agent already works. Retrofitting approval checkpoints into an agent that was built to run fully autonomously is far harder than designing them in from the start.

🏋️ Practice Questions

  2. Explain why an audit log, on its own, is not sufficient oversight for a high-stakes autonomous action.
🎤 One-Line Interview AnswerHuman-in-the-loop design combines three complementary mechanisms — reviewing the plan before any step runs, requiring explicit approval before specific high-stakes actions, and keeping a durable audit log of every action taken — gated by consequence so low-stakes steps stay autonomous and high-stakes ones always get real human review.

Module 15 — Interview Questions

Agent vs RAG · ReAct · Memory · Multi-agent

▼

Q: What's the practical difference between an AI agent, a chatbot, and a simple RAG application?

A chatbot answers one message and stops; it has no loop and no ability to act beyond producing text. A simple RAG app adds exactly one deterministic step — retrieve relevant documents, then generate an answer — but that sequence is fixed in advance, not decided at run time. An agent is open-ended: it decides, step by step, which tools to call, how many times, and in what order, based on what it has already observed, continuing until the goal is met or it stops itself. In practice, RAG often becomes just one tool an agent can choose to use, rather than a separate architecture.

Q: What is the ReAct pattern, and why does it actually improve reliability?

ReAct has the model write a short reasoning step, a "thought," before each tool call, stating what it's trying to find out and why this action is the right next step, instead of jumping straight from goal to action. This externalizes the model's intermediate reasoning, which makes wrong decisions visible and inspectable before they turn into a bad action, and reduces wrong or redundant tool calls compared to action-only prompting. The trade-off is real: every thought costs extra tokens and latency, so the right amount of reasoning scales with task difficulty rather than being maximized everywhere.

Q: Walk me through how tool or function calling actually works end to end.

The application sends the model the conversation plus a list of tool definitions — names, descriptions, and argument schemas. The model, instead of replying with plain text, can emit a structured request naming a tool and its arguments. The application parses and validates that request, executes the real function, and appends the result back into the conversation as a new message. The model is then called again with this extended history and decides whether to answer directly or call another tool — the model itself never executes anything; it only requests, and the host application is the one actually running code.

Q: How does agent memory differ between short-term and long-term, and when do you use each?

Short-term memory is the running context window for the current run — exact, but bounded, and it doesn't survive past that run. Long-term memory lives outside the context window, typically via periodic summarization to control token growth within a run, or via a persistent store like a vector database for facts that need to survive across sessions. Use summarization for information that's only useful as background for finishing the current task; use persistent storage for discrete, reusable facts likely to matter again later, like a stated user preference. Dumping everything into a long-term store indiscriminately actually hurts retrieval quality, so curation matters more than volume.

Q: When does a multi-agent system actually add value versus just adding complexity?

A single, well-scoped agent should be the default — most tasks, even multi-step ones, don't need separate agents coordinating. Multi-agent designs earn their cost when sub-tasks need genuinely different specialization that would otherwise bloat one agent's prompt past reliability, when sub-tasks can run in parallel for real speed gains, or when isolating a noisy sub-task's context keeps it from diluting the main agent's reasoning. Every extra agent adds coordination overhead, more places for miscommunication between agents, and roughly multiplies cost and latency, so I'd want a concrete reason, not just "the task feels complex," before splitting it up.

Q: How do you approach planning and task decomposition for a complex agent goal?

I break the goal into an ordered sequence of sub-tasks, either generated up front for complex, reviewable workflows or decided step by step when early results are likely to change what the right next step even is. The more important half is re-planning: treating that initial plan as a hypothesis, not a fixed script, and explicitly updating it when a step's actual result contradicts what was assumed, rather than mechanically continuing down an invalidated path. For anything with real side effects, I'd also surface the plan to a human before execution starts, since that's the cheapest point to catch a wrong approach.

Q: How should an agent handle a tool call that fails?

The failure should be caught and returned to the model as a normal tool result, not allowed to crash the loop, so the model can reason about what happened and decide the next move: retry with different arguments, try a different tool, or report the problem. I'd also track repeated failures explicitly; if the same call fails the same way more than once or twice, that should be surfaced to the model as "this didn't work before," or escalated to a human, rather than letting the agent retry indefinitely. Silent retries without that context are exactly how agents end up stuck in loops.

Q: What guardrails would you put around an agent that's allowed to take real-world actions?

Permission tiers on every action-capable tool: read-only or reversible actions run autonomously, moderate-risk actions run within hard limits, and high-stakes or irreversible actions always require human approval before executing, enforced in code at the point the tool runs, not as a prompt instruction the model is just asked to follow. On top of that, rate limits bound runaway cost or repeated mistakes, and sandboxing keeps risky tools like code execution away from production systems and secrets even if they're approved to run. Those layers are complementary: permissions decide whether an action is allowed, sandboxing limits what it can reach if it does.

Q: How do you evaluate whether an agent is actually working well?

I look at the whole trajectory, not just the final answer: task success rate against a programmatically checkable outcome, step efficiency relative to a reasonable minimum, cost and latency per run, and whether the tool calls made along the way were valid and actually necessary. A correct final answer can still hide a wasteful, risky, or lucky path, so success rate alone isn't enough. I'd build a small eval set that includes deliberately tricky cases, like a tool that returns an error or a misleading intermediate result, because those are exactly the situations a narrow happy-path eval would never catch, and exactly where agents tend to fail in production.

Q: Multi-step agent loops get expensive and slow — how do you manage that?

Cost and latency compound with every step, so the first lever is simply bounding steps with a sane max and catching repetitive or stuck behavior early rather than letting it run to the cap. Second, keep context lean: summarize older history and drop tool results that are no longer relevant, since a bloated context both costs more tokens per call and tends to degrade reasoning quality. Third, match reasoning effort to task difficulty instead of asking for maximal chain-of-thought on every step, and consider caching or reusing results for repeated sub-queries within a run. For multi-agent designs specifically, I'd also look hard at whether parallel execution of independent sub-tasks is possible, since that reduces wall-clock latency even when total token cost stays similar.

Q: Where would you put human-in-the-loop checkpoints in an agent design?

Gated by consequence, not by task type: low-stakes, reversible steps run autonomously no matter how many of them there are, while the rare high-stakes or irreversible action always pauses for explicit approval. For multi-step tasks I'd also add a single, cheap plan review before execution starts, showing the intended approach so a human can catch a wrong strategy at the lowest possible cost, before anything has actually run. And independent of either of those, every action gets logged to an audit trail, which supports debugging and accountability even when nothing goes wrong.

Q: What are the most common ways agents fail in practice?

Getting stuck in repetitive loops, retrying a failing approach with cosmetic variations because the model has no inherent memory of "I already tried this." Hallucinated tool calls or arguments, which are more dangerous here than a hallucinated fact in a plain chatbot answer because a fabricated argument can trigger a real action. Context-window overflow or degraded reasoning as a long run's history keeps growing unmanaged. And cascading errors, where an early wrong assumption becomes part of the "ground truth" every later step reasons from, producing an increasingly confident, increasingly wrong chain of actions.

Q: How do you prevent an agent from hallucinating a tool call?

Tight, well-scoped tool definitions with precise argument schemas reduce ambiguity the model could otherwise fill with a guess. I'd also validate every tool-call argument before execution exactly as I'd validate any other untrusted input, checking a referenced ID actually exists, a value matches the expected type and format, and return a clear "not found / invalid" result rather than letting a fabricated value propagate into a real action. Detecting and surfacing repeated or implausible calls back to the model, rather than silently executing them, also helps catch this class of error before it causes damage.

Q: What makes a good tool definition for an LLM agent?

A precise, unambiguous description of exactly what the tool does, with argument types and formats spelled out rather than left to inference, and a clear description of what it returns. Narrow, single-purpose tools are far more reliable than one broad tool with a free-text "instructions" argument, because there's less room for the model to misuse a tightly scoped interface. I'd also collapse multi-step API flows into a single tool call where possible, and return concise structured results with actionable error messages instead of a raw dump the model has to re-parse.

Q: How do you decide how many steps to allow an agent before stopping?

I'd start from the task's realistic complexity, estimating the minimum number of steps a competent run would need, and set the cap at a multiple of that, not an arbitrary round number. Below the hard cap, I'd also detect stuck or repetitive behavior earlier and stop or escalate before burning the full budget, since most runaway runs are identifiable well before the step limit is reached. The cap exists specifically to bound worst-case cost and prevent a confused agent from running indefinitely, so it should be tuned per task type rather than set once globally.

Q: What's the risk of giving an agent too much autonomy too early in a product's life?

Early on, you don't yet have the evaluation data or production failure history to know where the agent actually goes wrong, so overly broad autonomy means mistakes happen in front of real users or on real data before you've learned what to guard against. I'd start with a narrower, more supervised version, with tighter permission boundaries and more approval checkpoints, and deliberately widen autonomy as evaluation results and audit logs build confidence in specific, observed behavior, rather than assuming broad capability is safe because it works in a demo. A demo succeeding once says very little about failure rate at scale.

Q: How would you debug an agent that gave a wrong final answer after six steps?

I'd pull the full step trace — every reasoning step, tool call, and observation — and walk it forward rather than starting from the wrong answer and guessing backward. Because errors cascade, the wrong final answer is often just the visible symptom of a mistake several steps earlier, a misread tool result or a wrong assumption stated in an early reasoning step, so I'm looking for the first point where the agent's stated understanding diverges from what the tools actually returned. Once I find that point, I'd check whether it was a tool-design problem, a reasoning problem, or a prompting problem before deciding what to fix.

🎤 One-Line Interview AnswerAcross agentic-AI interviews, the strongest answers consistently connect a specific mechanism — the tool-calling round trip, a memory strategy, a guardrail — to a concrete trade-off, rather than describing agents in abstract, hype-driven terms.

Multi-agent orchestration is worth learning, but it's a late-stage topic — it's easy to over-invest in it before the fundamentals of a single reliable agent are solid.
